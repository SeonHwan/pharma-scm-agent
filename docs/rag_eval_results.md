## 2. 구현 중 결과를 보기 전에 고정한 세부 선택
프로토콜에 없던 세부 사항이다. 모두 실행 전에 코드와 docstring에 적었고 조정하지 않았다.
- 색인 텍스트: R0, R1은 운영 코드와 같이 "제목 제목 본문"(제목 2회). R2, R4는 "제목 본문".
- BM25(R1): k1=1.5, b=0.75, 질의 토큰은 중복 제거 후 한 번씩.
- R0는 운영 코드(`run_search_sop`)와 같은 순위와 점수를 내는지 테스트로 확인했다(기존 30개 섹션, v1 문항 20개의 상위 3개와 소수 셋째 자리 점수).
- R2: 질의에 지시문 접두어 없음, 정규화 벡터의 내적. R3: RRF k=60, 각 방식의 전체 순위를 결합. R4: R3 상위 20개를 리랭커로 재정렬, 21위 이하는 R3 순서 유지.
- **MRR에는 구간을 붙이지 않았다.** 사전 등록은 "각 값에 Wilson 95% 구간"이라고 적었지만 Wilson 구간은 비율(recall)에만 적용되는 방법이고 MRR은 비율이 아니다. 이 점이 사전 등록과 다르다.

둘 다 통과해 규칙(더 단순한 쪽)에 따라 **판정은 R3**다. 이 판정이 말하는 것은 "이 벤치마크의 낮은 겹침 질의에서, 현재 방식(R0)보다 recall@3이 23%p 높고 구간이 겹치지 않는다"까지다. 에이전트에 적용할지는 이 판정만으로 정하지 않는다(§6).

## 5. 해석
**말할 수 있는 것**
- 낮은 겹침 부류에서 R0(현재 방식)의 recall@3은 0.730이고, R3와 R4는 0.959다. 구간이 겹치지 않는다. 임베딩을 쓰는 R2, R3, R4가 R0, R1보다 모든 부류에서 높거나 같다(높은 겹침 부류에서는 R1, R2, R3, R4가 모두 0.99 이상으로 차이가 작다).
- R1(BM25)은 R0보다 점추정이 높지만 구간이 겹쳐 차이가 있다고 말할 수 없다(낮은 겹침 recall@3 0.784 대비 0.730).

**말할 수 없는 것, 조심할 것**
1. **R2(임베딩만)와 R3의 차이는 구분되지 않는다.** 낮은 겹침 recall@3은 R2 0.946, R3 0.959이고, 질의별로 R2만 맞힌 질의가 2개, R3만 맞힌 질의가 3개다. R2는 사전 등록된 채택 후보가 아니라서 판정에는 쓰지 않았다. 그러나 **BM25를 결합하는 이득은 이 데이터로 확인되지 않았다**(사후 관찰). 규칙의 판정이 R3인 것과 결합이 필요하다는 것은 다른 주장이다.
2. **R4의 이득은 recall@1에 있다.** recall@3은 R3와 같다(낮은 겹침 0.959). 낮은 겹침 recall@1은 R3 0.797 → R4 0.905다. 현재 에이전트는 상위 3개를 모두 읽으므로 이 이득이 최종 답에 반영되는지는 이 단계에서 알 수 없다.
3. **지연은 GPU에서 잰 값이다.** 운영(ECS Fargate)에는 GPU가 없고, CPU에서의 지연은 측정하지 않았다. 판정 규칙의 지연 기준을 배포 환경 기준으로 다시 확인해야 한다(추정: CPU에서는 R2가 수십 ms 이상, R4는 그보다 훨씬 클 수 있다. 확인되지 않은 값).
4. **운영 비용이 있다.** 임베딩과 리랭커를 쓰려면 운영 이미지에 PyTorch와 모델 파일(각 약 2GB)이 들어가야 한다. 현재 이미지는 `retrieval` 의존성 그룹을 뺐다. 이미지 크기, 콜드 스타트, 메모리가 늘어난다(측정하지 않음).
5. **낮은 겹침 부류는 거의 v2 질의다(73/74).** v1 문항(사람이 쓴 규정 질문)은 R0도 recall@3이 0.95이고 R1~R4는 1.0이라 천장에 닿아 차이를 볼 수 없다. 이 결과는 "섹션의 표현을 바꿔 쓴 질의"에서의 개선이고, 실제 사용자 질의에서의 개선은 확인하지 않았다.
6. 사전 등록 한계가 그대로 유효하다: 코퍼스와 질의가 합성이고 같은 계열 모델이 만들었다(검증은 다른 회사 모델과 사용자 샘플 20개로 부분적으로만 줄였다), 코퍼스 문서 사이에 모순이 있다(프로토콜 9-7), 이 단계는 검색만 평가한다(에이전트의 최종 답은 평가셋 v2 단계에서 따로 본다).
7. 질의 146개라 구간이 넓다. 같은 순위로 보이는 방식(R2/R3, R3/R4의 recall@3)은 구분되지 않는다.

## 6. 실패 질의 (사후 관찰, 판정과 무관)
recall@3에서 놓친 질의 수: R0 22개, R2 5개, R3 4개, R4 3개.
- R3가 놓친 4개(SOP-13-3, 13-6, 11-3, 14-3)는 겹침이 0.03~0.26으로 낮았고, 같은 문서의 다른 섹션이나 비슷한 주제의 다른 문서 섹션이 상위에 왔다. **질의와 섹션을 읽고 원인을 확인하지는 않았다**(혼동 쌍에서 틀린 것으로 보일 뿐이다).
- R4가 놓친 3개(SOP-20-1, 20-5, 23-2)는 R3가 놓친 질의와 겹치지 않는다. 방식마다 틀리는 질의가 다르다.

## 7. 다음에 결정할 일
- 에이전트의 `search_sop`에 R3 또는 R4를 연결할지: 위 3, 4(배포 환경의 지연과 이미지 비용)와 1(결합의 필요성)을 먼저 확인한 뒤 정한다. 연결한다면 평가셋 v2에서 에이전트 최종 답이 좋아지는지(검색 개선 → 답 개선)를 따로 잰다.
- 연결하지 않는다면 이 문서를 "검색 방식을 측정으로 비교했고, 임베딩이 어휘 방식보다 바꿔 쓴 질의에서 낫다는 것까지 확인했으며, 배포 비용 때문에 도입은 보류했다"의 근거로 쓴다.

## 8. 배포 환경(GPU 없음) 확인: CPU 지연과 메모리
사전 등록 실행(§3~§4)과 **별개의 사후 확인**이다. §4의 판정은 바꾸지 않는다. `src/pharma_scm/retrieval/cpu_check.py`로 같은 질의 49개(146개 중 3개마다 1개)를 CPU로 돌렸다. 원자료는 `eval/rag/latency_cpu.json`이다.

**한계**: 이 PC의 CPU 16코어에서 torch 스레드 수를 줄여 Fargate vCPU를 흉내 낸 근사다. 실제 Fargate는 CPU 종류가 다르고 0.5 vCPU는 1스레드보다 느릴 수 있다(측정하지 않음). 질의가 49개라 p95는 큰 쪽 3개 근처의 값이다.

### 질의당 지연(ms, CPU)
| 스레드 | R2 p50 / p95 | R3 p50 / p95 | R4 p50 / p95 |
|---|---|---|---|
| 16 | 118.7 / 188.4 | 126.2 / 172.1 | 2123.8 / 2768.5 |
| 4 | 84.4 / 96.4 | 84.5 / 97.6 | 3936.7 / 4287.2 |
| 2 | 134.1 / 164.6 | 135.0 / 156.0 | 5561.8 / 6134.6 |
| 1 | 198.3 / 235.3 | 198.1 / 235.5 | 10414.1 / 11597.4 |

- 판정 규칙의 지연 기준(R3 p95 1초 미만, R4 p95 2초 미만)을 CPU 값에 적용하면 **R3는 모든 스레드 수에서 통과**(최대 236ms), **R4는 모든 스레드 수에서 탈락**(최소 2768ms)한다.
- R2, R3는 16스레드가 4스레드보다 느리다(질의 하나가 짧아 스레드를 늘려도 이득이 없고 조정 비용이 든다고 추정, 원인은 확인하지 않음).
- CPU 순위는 GPU 실행과 같았다: R2, R3, R4 모두 49개 질의에서 1위와 상위 3개가 100% 일치. 따라서 §3의 품질 결과는 CPU에서도 같다고 볼 수 있다(49개 질의 범위).

### 메모리(프로세스 최대 상주 메모리, MB)
| 시점 | MB |
|---|---|
| 모델 올리기 전(torch 등 라이브러리와 코퍼스 로드) | 791 |
| bge-m3 로드 후 | 1,222 |
| 섹션 158개 임베딩 후(R2 준비 끝) | 2,493 |
| 리랭커 로드 후(R4 준비 끝) | 2,769 |

- 최대 상주 메모리는 한 번이라도 올라간 최댓값이다. 2,493MB는 섹션을 임베딩하는 동안의 일시적 피크가 섞여 있어 질의만 처리할 때의 상태보다 높을 수 있다(분리해서 측정하지 않음).
- 현재 Fargate 작업 정의는 API가 0.5 vCPU, 메모리 1,024MB다(`deploy/terraform-ecs/task_definitions.tf`). **R2, R3는 그 크기로 올라가지 않는다.**
- R2 색인(섹션 임베딩)은 16스레드에서 11.4초였다. 적은 vCPU에서는 더 걸리므로 서버 시작 때가 아니라 빌드 때 미리 계산해 두는 방식이 필요하다(측정하지 않음).

### 이 확인이 말하는 것
- **지연은 R3가 CPU에서도 문제없다.** 막히는 것은 메모리와 이미지 크기다.
- **R4는 CPU에서 지연 기준을 넘는다.** GPU 없이는 이 구성에서 채택할 수 없다.

## 9. 컨테이너 확인: Fargate 크기를 흉내 낸 로컬 실행 (2026-11-26)
운영 이미지(`Dockerfile`)를 이 PC(16코어)에서 `docker run --cpus <N> --memory 4g`로 실행해 쟀다. `--cpus`는 CFS 할당량이라 Fargate의 vCPU 제한과 같은 방식이지만, 하드웨어가 달라 절대값은 참고용이다. 지연은 `python -m pharma_scm.retrieval.probe`(질의 10개 x 3회, R3 상위 3개)로 쟀다.

### 처음 실행에서 드러난 문제
| 항목 | 값 | 원인(직접 확인) |
|---|---|---|
| 질의 지연(0.5 CPU) | p50 4,500ms, p95 4,802ms | 컨테이너 안에서도 `nproc`가 16이라 PyTorch가 스레드 16개를 띄우고, 0.5 CPU 할당량을 순식간에 다 써서 주기 대부분을 멈춰 있었다(CFS throttling) |
| 이미지 | 레이어 합 약 7.5GB | 색인 빌드 중 transformers가 safetensors 변환본(고정되지 않은 PR 리비전, 2.27GB)을 백그라운드로 더 받음, uv 다운로드 캐시(1.2GB)가 이미지에 남음 |
| 실행 경고 | `Permission denied` (모델 캐시 trees 파일) | 빌드 때 root가 만든 파일이 600 권한 |

스레드 수만 바꿔 같은 이미지로 잰 값(0.5 CPU): `OMP_NUM_THREADS=1` p95 779ms, `=2` p95 1,296ms, 지정 안 함(16) p95 4,802ms.

### 고친 것
- `ENV OMP_NUM_THREADS=1`(실행 단계에만, 색인 빌드에는 적용하지 않음).
- `DISABLE_SAFETENSORS_CONVERSION=1`(`retrieval/models.py`에서 설정. 로컬, CI, 이미지 모두 적용). 실행 때는 원래도 고정 리비전의 `pytorch_model.bin`을 읽었으므로 가중치는 바뀌지 않는다.
- uv 캐시는 BuildKit 캐시 마운트로, 모델 캐시는 `chmod -R a+rX`.

### 고친 뒤
| 항목 | 값 |

| 레이어 | 의존성 1.57GB(전 2.82GB), 모델 2.3GB, 색인 2.8MB(전 2.27GB). `docker images` 표시 5.91GB(전 11.1GB) |

| 서버 메모리(`docker stats`, 대기 상태) | 795MiB. 모델 가중치는 파일 매핑이라 회수 가능한 캐시로 분류되어 이 값에서 빠진다 |

| 권한 경고 | 사라짐 |

### 이 확인이 말하는 것
- 0.5 CPU에서도 판정 기준(R3 p95 1초 미만)은 통과하지만 여유가 적다(692ms, 그 위에 에이전트의 LLM 호출 시간이 더해진다). 1 CPU면 절반이 된다.
- 메모리는 대기 상태 약 0.8GB, 파일 매핑까지 약 2GB다. 현재 작업 정의(1,024MB)로는 모델 파일이 캐시에 머물 자리가 없어 디스크를 반복해서 읽게 될 수 있다(확인하지 않음).
- 그래서 AWS 확인(7단계)은 **1 vCPU, 메모리 3GB**로 올려 보는 것을 제안한다. Fargate에서 1 vCPU는 메모리 2~8GB를 고를 수 있다(알고 있는 기준, 이번에 확인하지 않음).
