# 면접 대비 개념 정리 (ECS Fargate · Terraform)

사용자가 직접 남기라고 한 항목과, 면접에서 꼭 이해하고 설명해야 하는 핵심을 모은 문서다. 구성 전체와 용어집은 `docs/ecs_deploy_walkthrough.md`에 있고, 여기에는 **개념 사이의 관계와 "왜"**만 적는다. 비유 없이 개념과 이 프로젝트의 실물로 설명한다.

근거 표기: **직접 확인**(이번 프로젝트에서 조회·실행해서 봄), **사용자 보고**, **알고 있는 기준**(일반 지식, 이번에 확인하지 않음). 면접에서는 이 구분 자체를 답변에 쓸 수 있다.

## 1. 서비스 · 태스크 · 타깃 그룹 · ALB의 관계 (가장 중요)

| 대상 | 역할 |
|---|---|
| 태스크 정의 | 태스크를 어떻게 띄울지 적은 명세(이미지, CPU, 메모리, 환경변수, 비밀, 역할). 수정하지 않고 리비전이 쌓인다 |
| **태스크** | 명세대로 **실제로 실행 중인 단위**. 컨테이너(앱 프로세스)가 들어 있고 자기 ENI와 사설 IP를 가진다. 수명이 있어서 죽거나 배포로 교체되면 새 IP로 대체된다 |
| **서비스** | 같은 태스크 정의로 태스크를 **N개 실행 상태로 유지**한다. 멈추거나 헬스 체크에 실패한 태스크는 내리고 새로 띄우며, 새 태스크를 타깃 그룹에 **등록**한다 |
| **타깃 그룹** | 등록된 태스크들의 **명단과 각각의 상태**(`initial`, `healthy`, `unhealthy`, `draining`, `unused`), 헬스 체크 설정을 가진다. 요청 대상이 되는 것은 `healthy`뿐이다 |
| **ALB** | 클라이언트가 보는 단일 진입점. 리스너 규칙으로 타깃 그룹을 지정하고, 명단의 정상 태스크에 요청을 **나눠 보낸다** |

- 서비스에 저장되는 로드 밸런서 설정은 **타깃 그룹 ARN, 컨테이너 이름, 컨테이너 포트** 세 가지뿐이다. ALB와 리스너는 서비스에 저장되지 않는다(직접 확인). ALB와 타깃 그룹은 리스너 규칙으로 따로 이어진다.
- 서비스 하나는 태스크 정의 하나(리비전 하나)만 가리키고 같은 태스크 N개를 유지한다. 서로 다른 태스크를 띄우려면 서비스를 따로 만든다. 배포 중에만 구·신 리비전 태스크가 잠깐 공존한다(알고 있는 기준).
- 타깃 그룹은 보안 그룹이 없다. 보안 그룹은 ALB, 태스크, RDS의 ENI에 붙는다(직접 확인).

**면접 한 줄**: 서비스가 태스크를 N개 유지하고 타깃 그룹에 등록하면, 타깃 그룹이 헬스 체크로 정상 명단을 관리하고, ALB가 그 명단으로 요청을 분산한다.

**서비스 태스크와 일회성 태스크** (직접 확인: 앱은 서비스가 `apply` 때 자동으로 띄웠고, 복원은 `run-task`로 한 번 실행)

| | 서비스로 띄운 태스크 | `run-task`로 띄운 일회성 태스크 |
|---|---|---|
| 시작 | 서비스가 생성될 때 `desired_count`만큼 자동 | 사람이 실행(콘솔 **Run new task**의 Application type **Task**, 또는 `aws ecs run-task`) |
| 관리 | 죽으면 서비스가 교체, 타깃 그룹에 IP 등록 | 아무도 관리하지 않음. 끝나면 `STOPPED`로 남음 |
| 쓰임 | 계속 떠 있어야 하는 앱 | 한 번 하고 끝나는 작업(DB 복원, 마이그레이션) |

- 콘솔과 CLI는 같은 API(`RunTask`, `CreateService`)를 부른다. 서비스가 없는 일회성 태스크에는 포트 매핑과 로드 밸런서 연결이 필요 없다.
- 일회성 작업에 서비스를 붙이면 끝날 때마다 다시 실행하므로 맞지 않는다.

## 2. 타깃 그룹이 왜 중간에 있는가
- ALB의 리스너는 요청을 **타깃 그룹으로만** 전달하도록 되어 있다(알고 있는 기준). 거치지 않는 선택지가 없다.
- 거치는 이점은 아래와 같다.

| 문제 | 타깃 그룹이 있을 때 |
|---|---|
| 태스크 IP가 배포·교체마다 바뀐다 | 서비스가 명단을 갱신한다. ALB는 명단만 본다 |
| 죽은 태스크로 요청이 간다 | 헬스 체크를 통과한 태스크에만 보낸다 |
| 배포 중 처리 중인 요청이 끊긴다 | 교체될 태스크를 명단에서 먼저 빼고 처리할 시간(등록 해제 지연)을 준다 |
| 태스크가 여러 개면 나눌 방법이 없다 | 정상 태스크들에 분산한다 |

- 우리는 태스크가 1개라서 분산의 이점은 쓰지 않았고, IP 추적·헬스 체크·배포 중 연결 유지가 실제 이점이다.

## 3. 태스크를 N개 두는 이유
| 목적 | 내용 |
|---|---|
| 가용성 | 하나가 죽어도 나머지가 응답한다. 서로 다른 AZ에 두면 한 AZ 장애에도 버틴다 |
| 처리량 | 요청이 늘면 같은 태스크를 더 띄워 나눠 처리한다. 장애와 무관한 목적이다 |
| 무중단 배포 | 일부씩 교체하는 동안에도 응답할 태스크가 남는다 |

- 조건: 태스크 안에 상태를 쌓아 두지 않아야 한다(요청이 어느 태스크로 가도 같은 결과). 우리 앱은 데이터를 RDS에 두지만 앱 안의 메모리 상태 유무는 **확인하지 않았다**.
- **역할 분리**: 서비스는 N개를 존재하게 하고(공급), 타깃 그룹은 정상 여부를 판정하고, ALB는 나눠 보낸다. 죽은 태스크가 생기면 타깃 그룹이 즉시 요청 대상에서 제외하고(끊김 방지), 서비스가 새 태스크로 수를 되돌린다(복구).
- 우리 구성은 태스크 **1개**(비용과 학습 범위 때문). 교체되는 동안 응답이 끊길 수 있고 한 AZ 장애에 약하다. 운영이라면 2개 이상과 AZ 분산이 한계 보완책이다.

## 4. 클러스터와 Fargate
- **클러스터**: 서비스와 태스크를 담는 논리적 소속. 서비스는 반드시 어떤 클러스터에 속한다(서비스 생성 화면에서 직접 겪음). Fargate만 쓰고 서비스가 1개인 우리 구성에서는 이름표 수준이고, EC2 방식에서는 서버 풀로서 의미가 크다. 환경 분리, capacity provider, 클러스터 단위 지표·권한에도 쓰인다(알고 있는 기준).
- **Fargate**: 서버 종류가 아니라 **컨테이너 실행 방식**이다. 태스크마다 AWS가 격리된 실행 환경을 준비하고, 우리는 태스크 정의에 CPU·메모리만 적는다. 호스트에 SSH로 들어갈 수 없고, 과금은 태스크가 켜져 있는 시간(초 단위)이다. 태스크마다 ENI와 사설 IP를 가진다(IP는 직접 확인).
- 실행 방식은 두 곳에서 맞물린다: 태스크 정의의 `requires_compatibilities`(가능한 목록)와 서비스의 `launch_type`(실제 선택). Fargate면 태스크 정의에 `cpu`·`memory`(태스크 단위), `network_mode = awsvpc`, 실행 역할이 필요하다(알고 있는 기준).
- EC2 방식은 서버 1대에 여러 태스크가 올라갈 수 있고 서버 관리가 우리 몫이다.

## 5. 네트워크: VPC · 서브넷 · AZ · ALB 배치
- **VPC**는 계정(리전)마다 하나가 기본으로 주어진다. 서울 기본 VPC는 `172.31.0.0/16`, AZ마다 서브넷이 있다(직접 확인: 2a·2b·2c·2d가 각각 `/20`).
- **서브넷의 목적**은 주소를 나누는 것이 아니라, 구역마다 **위치(AZ)와 경로(경로표)**를 따로 정하는 것이다. 서브넷은 정확히 한 AZ에 속하고, 경로표에 인터넷 게이트웨이 경로가 있으면 공용, 없으면 비공개 서브넷이다.
- **IP는 ENI가 가진다.** 서브넷은 자원이 소유하는 것이 아니라 자원의 ENI가 놓이는 자리다. IP를 받는 것은 ALB(노드마다), 태스크, RDS의 ENI다. 타깃 그룹과 보안 그룹은 IP가 없다.
- **ALB는 고른 서브넷마다 노드를 하나씩 둔다.** DNS가 노드 IP들을 돌려주고 클라이언트가 하나로 접속한다. 태스크는 ALB가 활성화한 AZ 중 어디에 있어도 닿는다(교차 영역 분산은 알고 있는 기준).
- **AZ 불일치 사례(직접 확인)**: 서비스에 서브넷 4개를 허용했고 ECS가 ALB가 없는 2d에 태스크를 놓았다. 타깃이 `unused`가 되고 태스크가 교체됐다. 교체의 인과는 추정이다. 대응: ALB와 서비스가 **같은 서브넷 변수**를 쓰게 한다.
- NAT Gateway는 비공개 서브넷의 태스크가 **밖으로 나가는** 길을 준다(막는 장치가 아님). 비용이 커서 쓰지 않고 공용 서브넷에 공인 IP를 붙였다. 트레이드오프: 태스크가 공인 IP를 가진다.

## 6. 보안 그룹 사슬과 비밀 관리
- 보안 그룹은 각 자원의 ENI에 붙는 **상태 저장 허용 목록**이다. 막히면 오류 없이 시간 초과로 나타난다.
- 사슬: `alb-sg`(허용 IP:80) → `task-sg`(**ALB 보안 그룹**을 출처로 8000) → `rds-sg`(**태스크 보안 그룹**을 출처로 5432). 출처를 IP가 아니라 보안 그룹으로 지정해서 태스크 IP가 바뀌어도 규칙이 유지된다.
- **비밀**: SSM Parameter Store의 SecureString에 두고, **실행 역할**이 컨테이너 시작 전에 읽어 환경변수로 주입한다. 앱이 요청 중에 SSM을 호출하는 것이 아니다. 이미지에 비밀을 넣지 않는 이유: 레이어가 남고, 이미지를 받을 수 있는 사람이 읽고, 불변 태그가 이력을 보존하고, 교체하려면 다시 빌드해야 하고, 같은 이미지를 환경마다 쓸 수 없다.
- **실행 역할**(ECR 이미지 받기, SSM 읽기, 로그 쓰기)과 **태스크 역할**(앱 코드가 AWS를 호출할 때)은 별개다. 우리 앱은 AWS를 호출하지 않아서 태스크 역할은 없다.
- **`AmazonECSTaskExecutionRolePolicy`**(알고 있는 기준)는 AWS가 만들어 둔 권한 묶음으로 ECR 이미지 받기와 CloudWatch 로그 쓰기만 들어 있다. 이름의 "execution"은 앱 코드가 아니라 **ECS가 태스크를 시작하고 준비하는 과정**을 뜻한다. **SSM 읽기 권한은 없어서** 인라인 정책 `ssm-read-pharma`를 따로 붙였다.
- 태스크 정의의 `execution_role_arn` 자체가 **선택 항목**이다(공개 이미지에 로그·비밀이 없으면 불필요, 이전 `nginx` 연습). 필요한 것은 특정 정책 이름이 아니라 **시작에 필요한 일에 맞는 권한**이고, 같은 권한을 직접 쓴 정책으로 대체해도 된다. 권한이 없으면 앱 코드가 돌기 전 **시작 단계에서** 이미지 받기·로그 초기화 오류로 실패한다(예상, 직접 일으켜 보지 않음).
- 헬스 체크: `/health`(프로세스 생존, 타깃 그룹용)와 `/ready`(DB와 키 확인)를 분리했다. `/ready`를 타깃 그룹에 쓰면 DB 장애 때 태스크가 계속 교체되는 반복이 생긴다.

## 7. Terraform 핵심
- **무엇인가**: 인프라를 코드(`.tf`)로 선언하고, 선언과 현재 상태의 차이를 `plan`으로 보고 `apply`로 반영하는 도구. 만든 것은 **state**에 기록하므로 `destroy`가 만든 것만 지운다. 콘솔로 만들면 기록이 남지 않고 철거에서 누락이 생긴다(실제로 보안 그룹이 남았다).
- **provider**: terraform 본체는 AWS를 모른다. AWS API 호출 방법과 자원 종류는 provider 플러그인이 안다. `init`이 내려받는다. 새 권한을 주지 않고 `AWS_PROFILE`의 자격 증명으로만 호출한다.
- **AWS CLI와의 관계**: terraform은 CLI를 실행하지 않고 **같은 AWS API를 직접 호출**한다(알고 있는 기준).
- **파일 이름은 관례**다. terraform은 폴더의 `*.tf`를 전부 읽어 하나로 합친다. 변수 값은 `-var`, `terraform.tfvars`, `TF_VAR_*`, 기본값, 입력 질문 순으로 찾는다.
- **state는 코드가 아니라 AWS 자원의 기록**이다. 코드(원하는 상태), state(기억하는 상태), AWS(실제 상태) 셋을 구분한다. `plan`은 AWS를 조회해 state를 갱신한 뒤 코드와 비교한다. 로컬 `terraform.tfstate`는 비밀번호가 들어갈 수 있어 git에서 제외하고, 잃으면 `import`를 다시 해야 한다.
- **resource는 "만들어라"가 아니라 "이런 것이 있어야 한다"는 선언**이다. 없으면 `plan`이 `to add`, `apply`가 만든다. 있으면 `import`로 state에 연결한다(이번 실습: 6 imported, 이후 `plan`은 `No changes`). 자원 간 참조(`aws_security_group.alb.id`)가 곧 생성·삭제 순서(의존성)다.
- 안전 습관: `apply` 전에 `plan`에서 **삭제·교체 건수**를 먼저 읽는다. 이름·설명 변경은 자원을 지우고 다시 만들 수 있다.
- **`resource`와 `data`**: `resource`는 Terraform이 만들고 관리하는 자원, `data`는 이미 있는 것을 **읽기만** 한다(둘 다 state에 기록). 이 프로젝트에서 `data`는 기본 VPC, 서브넷 목록, SSM의 DB 비밀번호다. SSM 파라미터 7개는 코드로 만들지 않고 읽기만 해서 철거해도 남는다.
- **저장한 plan으로 apply**: `plan -out=파일`로 확정한 계획을 `apply 파일`로 실행하면 확인 질문 없이 **방금 읽은 변경만** 일어난다. plan 파일에는 비밀번호가 평문으로 들어가므로 쓰고 나면 지운다.
- **`-target`**: 지정한 자원과 **그것에 의존하는 자원만** 대상으로 한다. 평소에는 쓰지 않고(경고가 나옴), 이번에는 "과금 자원만 철거"와 "타깃 그룹만 먼저 만들기"에 썼다. 실제 `plan -destroy -target`으로 RDS, ALB, 서비스를 지정하자 리스너(ALB에 의존)와 복원 태스크 정의(RDS 주소를 참조)가 함께 5개로 계산됐다(직접 확인). 의존 관계는 참조로 정해진다. 참조가 없는 순서(서비스는 리스너가 있어야 만들어짐)는 `depends_on`으로 적는다.
- **목록 변수**: 허용 IP처럼 값이 여러 개일 수 있는 입력은 `list(string)`과 `validation`(`alltrue`, `0.0.0.0/0` 금지)으로 받는다.
- **이미지 태그를 변수로**: 태스크 정의는 불변이라 태그를 바꾸면 새 리비전이 생기고 서비스가 그 리비전으로 교체된다. 8단계 CD에서 git 해시 태그를 넣는 자리다.
- 비밀 값 규칙: 코드와 문서에 계정 ID, SG·VPC 같은 실제 ID, 실제 IP를 적지 않고, `terraform.tfstate`와 `terraform.tfvars`는 git에서 제외한다.

## 8. 면접에서 "검증하지 않은 것"을 말하는 법
이 프로젝트에서 직접 확인하지 못한 것은 숨기지 않고 구분해서 말한다.
- 서킷 브레이커의 **자동 롤백**: 이미지를 받지 못하는 리비전으로는 관찰했다(11절). **정확한 실패 임계값**, 앱이 떠서 헬스 체크에 실패하는 경우, 수동 롤백은 확인하지 않았다.
- 같은 PC에서 목적지마다 출구 공인 IP가 달랐다(직접 확인: 3가지). SG에 하나만 넣었을 때는 ALB 접속이 시간 초과였고 3개를 모두 허용하자 접속됐다. **ALB가 실제로 본 IP가 셋 중 무엇인지는 확인하지 않았다.**
- 태스크 1개 구성의 가용성 한계와 앱의 무상태 여부.
- 비용 실측: 크레딧 잔액만 확인했고 서비스별 사용액은 다음 확인 항목이다.

## 9. 이미지와 ECR (7단계 실행에서 겪은 것)
- **ECR은 컨테이너 이미지 저장소**이고 git 저장소가 아니다. 이미지는 `docker push`로만 올린다. `docker login`은 ECR의 레지스트리 자격을 이 컴퓨터에 저장하는 것이고(토큰 약 12시간), 이후 `docker push`가 그 자격으로 올린다.
- **이미지 이름은 `레지스트리/저장소:태그`**이고 빌드할 때의 이름과 push할 때의 이름이 같아야 한다. 다르면 push할 대상이 없다. 태그는 **불변**으로 설정해서 같은 태그를 덮어쓸 수 없다(배포 이력 보존).
- **빌드 컨텍스트**는 `docker build`의 마지막 인자 폴더다. 그 폴더 안의 파일만 `COPY`할 수 있고, `.dockerignore`도 그 컨텍스트 기준으로 적용된다. `-f`는 Dockerfile 위치를 고른다. 복원 이미지는 `deploy` 폴더를 컨텍스트로 하고 `deploy/.dockerignore`가 허용 목록 방식이다.
- **CPU 아키텍처**: 태스크 정의의 `cpu_architecture`와 이미지가 맞아야 한다. 이번에는 둘 다 `X86_64`/`amd64`였다. Apple 실리콘 맥에서 빌드하면 `--platform linux/amd64`가 필요하다(알고 있는 기준).
- **zsh 함정(직접 겪음)**: `$REPO:restore-...`에서 zsh가 `:r`을 변수 수식자로 해석해서 이미지 이름이 `...agentestore-...`로 망가졌다. `"${REPO}:restore-${TAG}"`처럼 중괄호와 따옴표로 감싼다.
- **복원은 일회성 태스크**: 같은 ECR 저장소에 다른 태그(`restore-해시`)로 올린 이미지를 쓰고, 서비스 없이 `run-task`로 한 번 실행한다. 스크립트는 `products` 테이블이 있으면 중단해서 두 번 복원되지 않는다(직접 확인: 처음 실행 때 행 수가 기대값과 모두 일치).

## 10. GitHub Actions → AWS: OIDC (8단계에서 겪은 것)
**왜 쓰나**: 워크플로가 AWS를 호출하려면 자격이 필요하다. 장기 액세스 키를 GitHub 시크릿에 넣으면 유출되면 계속 쓸 수 있는 키가 된다. OIDC는 키를 저장하지 않고, **워크플로가 실행될 때마다 GitHub이 서명한 신원 토큰을 발급**하고 AWS가 그 토큰으로 **임시 자격**을 준다.

**흐름** (이 프로젝트의 `deploy.yml`의 "AWS 역할 맡기" 단계):
1. job에 `permissions: id-token: write`가 있어야 GitHub이 그 job에 토큰을 발급한다.
2. 액션(`configure-aws-credentials`)이 토큰을 AWS STS(Security Token Service)의 `AssumeRoleWithWebIdentity`에 보낸다.
3. STS가 **역할의 신뢰 정책**과 토큰의 값(claim)을 비교하고, 맞으면 임시 자격(수 시간 이내 만료)을 돌려준다. 이 자격이 그 job의 환경변수가 된다.
4. 이후 단계(ECR 로그인, ECS 배포)는 그 역할의 **권한 정책**이 허용하는 일만 한다.

**두 정책의 역할이 다르다**
| | 정하는 것 | 이 프로젝트 |
|---|---|---|
| 신뢰 정책(assume role policy) | **누가** 이 역할을 맡을 수 있는가 | `aud`가 `sts.amazonaws.com`, `sub`가 이 저장소의 master 브랜치 |
| 권한 정책 | 맡은 뒤 **무엇을** 할 수 있는가 | ECR push, 태스크 정의 등록, 서비스 갱신, 실행 역할 `PassRole` |

**토큰의 claim**: `iss`(발급자), `aud`(대상, AWS용은 `sts.amazonaws.com`), `sub`(누구인가: 저장소·브랜치). 신뢰 정책 조건이 `aud`와 `sub`를 비교한다. AWS 계정에는 먼저 "GitHub 토큰을 검증할 수 있다"는 **OIDC 공급자**를 한 번 등록해야 한다.

**겪은 일: `sub` 형식 (직접 확인)**
- 신뢰 정책에 `repo:SeonHwan/pharma-scm-agent:ref:refs/heads/master`(이름 형식)를 넣었더니 역할 맡기가 `Not authorized to perform sts:AssumeRoleWithWebIdentity`로 실패했다.
- 이 저장소의 설정을 조회하니(`gh api repos/소유자/저장소/actions/oidc/customization/sub`) `use_immutable_subject: true`였고 `sub_claim_prefix`에 소유자와 저장소의 **숫자 ID**가 붙어 있었다. 신뢰 정책을 그 형식으로 바꾸자 통과했다.
- 불변 형식을 쓰는 이유는 저장소를 지우고 같은 이름을 다른 사람이 만들어도 숫자 ID는 달라 그 역할을 맡지 못하게 하려는 것으로 알고 있다. 이름 형식을 옛 값으로 같이 남기면 이 목적이 사라진다.
- 토큰의 실제 `sub`를 찍어 본 것은 아니다. 수정 뒤 통과한 것으로 확인했다.

**`iam:PassRole`**: 새 태스크 정의 리비전에 실행 역할을 지정하려면, 호출자가 그 역할을 ECS에 **넘길 권한**이 필요하다. 정책에서 대상을 실행 역할 하나로, 받는 서비스를 `ecs-tasks.amazonaws.com`으로 제한했다. 이 권한을 넓히면 배포 역할이 더 센 역할을 태스크에 붙여 권한을 키울 수 있다(알고 있는 기준).

**권한을 좁히는 방식**: 자원 단위로 좁힐 수 없는 동작(`ecr:GetAuthorizationToken`, 태스크 정의 조회·등록)만 `"*"`로 허용하고 나머지는 ECR 저장소 하나, 서비스 하나, 실행 역할 하나로 제한했다. 서비스 ARN은 서비스 자원을 참조하지 않고 문자열로 조립했다(참조하면 서비스가 없을 때 이 정책을 만들면서 서비스, 즉 과금 자원까지 만들게 되기 때문).

**면접 한 줄**: GitHub이 워크플로 실행마다 서명된 토큰을 주고, AWS가 신뢰 정책(저장소·브랜치 조건)으로 검증해 임시 자격을 주므로 장기 키가 없다. 맡은 뒤의 권한은 별도의 최소 권한 정책이 정한다.

## 11. 서킷 브레이커와 롤링 배포의 롤백 (8단계에서 관찰한 것)
**롤링 배포**: 서비스의 태스크 정의를 새 리비전으로 바꾸면 ECS가 새 태스크를 띄우고, 정상으로 확인되면 옛 태스크를 내린다. 새 태스크가 정상이 되기 전에는 옛 태스크가 계속 서비스한다. 태스크 정의의 리비전은 덮어쓰지 않고 번호가 늘어난다.

**서킷 브레이커**: 서비스 설정 `deployment_circuit_breaker { enable = true, rollback = true }`. 새 태스크가 계속 시작에 실패하면 배포를 실패로 표시하고 **직전에 안정되었던 배포(리비전)로 서비스를 되돌린다**.

**관찰 (직접 확인, 시나리오: 이미지 태그가 없는 리비전 6)**
| 시각(KST) | 사건 |
|---|---|
| 11:59:08 | 서비스를 리비전 6으로 변경 |
| 11:59:22부터 | 새 태스크가 시작되고 `CannotPullContainerError ... not found`로 실패, 약 1분 반 간격으로 반복 |
| 12:13:06 | `deployment failed: tasks failed to start` → `rolling back to deployment ...` |
| 12:13:38 | 리비전 5로 안정(`steady state`), `/health`·`/ready` 200 |
- 롤백까지 약 14분이 걸렸다. 그동안 리비전 5의 태스크는 running 1을 유지했다(30초 간격 기록 기준).
- 롤백은 **서비스만** 되돌린다. 실패한 리비전 6은 등록된 채 남는다(`deregister`로 비활성화). 이후 패밀리 이름으로 `describe-task-definition`하면 최신 리비전을 주므로, CD가 "현재 정의"를 받아 이미지만 바꾸는 방식이면 이 점을 알고 있어야 한다.

**확인하지 않은 것**: 정확한 실패 횟수 임계값(`failedTasks` 최댓값 3까지만 봤고 롤백 시점의 값은 못 봤다), 앱이 떠서 헬스 체크에 실패하는 경우, 수동 롤백(`update-service`로 이전 리비전 지정), 롤백이 일어났을 때 deploy 액션이 실패로 끝나는지.

**면접 한 줄**: 롤링 배포 중 새 태스크가 계속 실패하면 서킷 브레이커가 배포를 실패 처리하고 직전 리비전으로 자동 복귀시킨다. 일부러 망가뜨린 리비전으로 이 동작을 실제로 관찰했고, 그동안 옛 태스크가 서비스를 유지했다.

## 12. Terraform과 CD의 역할 분담: `ignore_changes`
**문제**: Terraform 코드는 서비스의 `task_definition`을 특정 리비전(코드가 만든 것)으로 적는다. CD는 새 리비전을 만들어 서비스를 바꾼다. 그 뒤 `terraform plan`은 "서비스가 코드와 다르다"고 보고 옛 리비전으로 되돌리려 한다.

**해법**: `aws_ecs_service`에 `lifecycle { ignore_changes = [task_definition] }`. 이 항목은 **Terraform이 서비스를 처음 만들 때만 정하고**, 이후의 변경은 비교하지 않는다. 역할 분담은 아래와 같다.
| | 담당 |
|---|---|
| 인프라(서비스, ALB, RDS, IAM 등 틀) | Terraform |
| 서비스가 어느 이미지 리비전을 쓰는가 | CD(GitHub Actions) |

**확인 (직접 확인)**: CD가 서비스를 리비전 5로 바꾼 뒤(Terraform 상태는 리비전 4) `terraform plan`이 `No changes`였다.

**함께 알아 둘 점**
- `UpdateService`는 **부분 갱신**이다. CD는 `service`, `cluster`, `task-definition`만 넘기고, FARGATE, 서브넷, 보안 그룹, 타깃 그룹 연결, desired count, 서킷 브레이커 설정은 서비스에 저장된 값이 그대로 유지된다.
- 컨테이너 이름(`api`)과 포트는 서비스의 `load_balancer` 설정과 태스크 정의가 일치해야 한다. CD가 이미지 값만 바꾸므로 유지된다.
- 철거 뒤 `apply`로 서비스를 다시 만들면 Terraform 상태에 기록된 옛 리비전(4)으로 시작한다. 그다음 CD가 최신 이미지로 바꾼다.
- 코드가 이미지 태그를 변수(`app_image_tag`)로 받는 것은 **처음 만들 때의 값**일 뿐, 이후 실제 이미지는 CD가 정한다.

**면접 한 줄**: 인프라는 Terraform이, 배포되는 이미지 리비전은 CD가 담당하게 나누고, 둘이 충돌하지 않도록 서비스의 `task_definition`을 `ignore_changes`로 두었다. 이후 `plan`에서 변경 없음으로 확인했다.

## 13. CI와 CD (이 프로젝트의 워크플로 구분)
| | 질문 | 하는 일 |
|---|---|---|
| CI(Continuous Integration) | 이 변경을 합쳐도 되는가 | 변경마다 린트·테스트·빌드를 자동으로 돌려 깨졌는지 확인 |
| CD(Continuous Delivery/Deployment) | 검증된 변경을 환경에 내보낼 수 있는가 | 이미지 빌드 → 저장소 push → 서비스 반영 |
- **Delivery**: 배포 가능한 상태까지 자동으로 만들고 실제 배포는 사람이 승인·실행한다. **Deployment**: 검증을 통과하면 사람 개입 없이 자동 배포한다.
- 이 프로젝트: `ci.yml`(push·PR마다 ruff, pytest(DB 복원 포함), Docker 빌드)과 `eval-smoke.yml`(평가 관련 경로를 바꾼 PR의 스모크 평가 게이트)이 CI, `deploy.yml`이 CD다. `eval-full.yml`은 기준선 근거 수집용 수동 평가로 배포와 무관하다.
- `deploy.yml` 안의 `gate` job은 CI와 같은 일(테스트, 평가)을 배포 직전에 한 번 더 한다. 배포 워크플로가 "이 커밋이 지금 안전한가"를 스스로 확인하게 하려는 설계이고, 대가로 단계가 여러 파일에 중복된다.
- CI는 AWS에 접근하지 않아 OIDC 역할이 필요 없고, CD만 AWS 역할을 맡는다.
- **면접에서**: CI는 push마다 동작한 기록이 있다. CD는 수동 트리거로 실제 배포와 롤백 관찰까지 확인했다(10~12절, 실행 기록은 `docs/ci_operations.md`). 확인하지 않은 범위(10~12절, 8절)는 구분해서 말한다.

## 14. 워크플로 단계의 성공·실패와 종료 코드
- GitHub Actions는 `run` 단계의 **프로세스 종료 코드**로 성공(0)과 실패(0이 아님)를 판단한다. 실패한 단계 뒤의 단계는 `if: always()` 같은 조건이 없으면 실행되지 않는다. `needs`로 이어진 뒤 job은 앞 job이 실패하거나 건너뛰어지면 실행되지 않는다(`deploy`가 `gate`에 의존).
- **`run_eval --strict`**: 문항 실행 중 **예외로 실패한 문항**이 있으면 종료 코드 1이다. 답이 틀린 것은 실패가 아니다(직접 읽은 코드). 정답률과 안전 같은 품질 판정은 별도의 `gate.py`가 `eval/baseline.json` 기준으로 하고, 위반이 있으면 종료 코드 1이다. 집계(`report --json`)는 실패 경로가 없다.
- 종료 코드 126은 "실행 권한이 없거나 실행할 수 없음", 127은 "명령을 찾을 수 없음"이다(알고 있는 기준). 이번에 126을 `Permission denied`와 함께 직접 겪었다(15절).
- 값을 `run` 안에서 쓸 때는 `${{ }}`를 스크립트에 직접 끼우지 않고 `env:`로 환경변수에 넣어 쓴다. 입력 문자열이 명령으로 해석되는 것을 막는다.

## 15. git의 실행 비트 (직접 겪은 것)
- git은 파일마다 **모드**를 기록한다. 종류는 `100644`(일반 파일), `100755`(실행 가능), `120000`(심볼릭 링크)이 대표적이다. 소유자·그룹 같은 세세한 권한은 기록하지 않고 **실행 비트의 유무**만 기록한다.
- 저장소를 받는 쪽(CI 러너 포함)은 기록된 모드대로 파일을 만든다. `scripts/ci_restore_db.sh`가 `100644`로 커밋되어 있어 워크플로의 `run: scripts/ci_restore_db.sh`(직접 실행)가 `Permission denied`, 종료 코드 126으로 실패했다. 이 PC의 파일은 `rwxr-xr-x`라서 로컬에서는 몰랐다(`git diff`는 `old mode 100644, new mode 100755`).
- 영향: `ci.yml` 최근 실패 4건이 모두 이 원인이었다(로그 4건 직접 확인). 모드를 `100755`로 커밋한 뒤 `ci.yml`이 처음 성공했다.
- 해법 두 가지: 모드를 커밋하거나(`git update-index --chmod=+x`, 또는 로컬에서 `chmod +x` 후 add), 워크플로에서 `bash scripts/...`처럼 인터프리터로 실행해 모드에 기대지 않는다. 이번에는 앞의 방법으로 한 번에 여러 워크플로를 고쳤다.

## 16. ARN
- **ARN(Amazon Resource Name)**은 AWS 자원의 고유 주소이고 형식은 `arn:파티션:서비스:리전:계정ID:자원`이다. 예: ECS 서비스는 `arn:aws:ecs:리전:계정ID:service/클러스터/서비스`.
- IAM 정책의 `Resource`에 ARN을 적어 "이 자원에만" 허용한다. 자원 단위로 좁힐 수 없는 동작은 `"*"`를 쓴다(8단계 `deploy-ecs` 정책의 `EcrLogin`, `EcsTaskDefinition`).
- Terraform에서 `aws_iam_role.x.arn`처럼 **자원을 참조**하면 의존 관계가 생겨 그 자원이 먼저 만들어진다. 문자열로 ARN을 조립하면 의존이 생기지 않는다. 서비스를 지운 상태에서 정책을 만들 때 서비스까지 만들어지는 것을 피하려고 서비스 ARN만 조립했다(직접 겪은 이유).
- 계정 ID가 들어 있어 코드·문서에 실제 값을 적지 않는다. GitHub 변수 `AWS_ROLE_ARN`에도 저장은 하되 문서에는 값을 적지 않는다.

## 17. 규정 검색: BM25, 임베딩, RRF, 재정렬
- **BM25**: 질의 단어가 문서에 몇 번 나오는지(많을수록 높지만 점점 덜 오른다, k1)와 문서 길이(긴 문서는 깎는다, b), 단어의 희귀함(IDF)으로 점수를 매긴다. 단어가 같아야 맞는다. 이 프로젝트는 k1=1.5, b=0.75, 제목을 2번 넣어 제목 가중을 줬다.
- **밀집 임베딩(bge-m3)**: 질의와 섹션을 각각 1024차원 벡터로 만들고 정규화한 뒤 내적(코사인)으로 순위를 매긴다. 단어가 달라도 뜻이 가까우면 맞을 수 있다. 섹션 벡터는 빌드 때 한 번 계산하고, 질의만 요청 때 계산한다.
- **RRF(Reciprocal Rank Fusion)**: 점수가 아니라 **순위**를 합친다. 각 방식에서 r위인 문서에 1/(k+r)을 더한다(k=60). BM25 점수와 코사인 점수는 단위가 달라 그대로 더할 수 없어서 순위를 쓴다.
- **재정렬(교차 인코더)**: 질의와 섹션을 한 쌍으로 모델에 넣어 관련도를 직접 계산한다. 정확할 수 있지만 후보마다 모델을 돌려서 느리다. CPU에서 p95 2.8~11.6초라 채택하지 않았다(직접 측정).
- 결과(사전 등록 벤치마크, 질의 146개): 단어가 적게 겹치는 질의 74개에서 상위 3개 정답률 TF-IDF 73.0%, BM25 78.4%, 임베딩 94.6%, RRF 95.9%. 임베딩과 RRF는 구분되지 않았고(유일하게 맞힌 문항 2개 대 3개), 사전 등록 규칙에 따라 RRF를 골랐다.

## 18. recall@k, MRR, Wilson 구간, McNemar 검정
- **recall@k**: 정답 섹션이 상위 k개 안에 있는 질의의 비율. **MRR**: 정답 순위의 역수(1위 1, 2위 0.5 ...) 평균.
- **Wilson 95% 구간**: 비율(k/n)의 신뢰 구간. n이 작거나 비율이 0·1에 가까워도 범위를 벗어나지 않는다. 두 방식의 구간이 겹치지 않는 것을 채택 조건 중 하나로 썼다.
- **McNemar 정확 검정**: 같은 문항을 두 조건으로 풀었을 때 **엇갈린 문항**(한쪽만 맞힌 문항) b, c만 본다. 차이가 없다면 엇갈림은 반반이므로 min(b, c) 이하가 나올 이항 확률의 2배가 p값이다. 짝지은 비교라 문항 난이도 차이가 상쇄된다.
- 평가셋을 dev와 test로 나누고, 개선안은 dev만 보고 정한 뒤 test는 한 번만 돌린다. dev에서 고르면 dev 결과가 낙관적이기 때문이다.

## 19. 컨테이너의 CPU 할당량과 스레드 (직접 겪은 것)
- `docker run --cpus 0.5`와 Fargate vCPU는 CFS 할당량이다: 100ms마다 CPU 시간을 50ms까지 쓸 수 있다. 코어 수가 줄어드는 것이 아니라 시간이 제한된다.
- 컨테이너 안의 PyTorch는 호스트 코어 수(이 PC 16개)만큼 스레드를 띄웠다. 16개가 동시에 돌면 50ms를 약 3ms 만에 다 쓰고 남은 시간 동안 멈춘다(throttling). 질의 하나가 4.5초 걸렸고, `OMP_NUM_THREADS=1`로 0.7초가 됐다(직접 측정).
- 로컬 `--cpus`는 CPU **개수**는 흉내 내지만 **세대와 클럭**은 흉내 내지 못한다. 같은 1 CPU에서 로컬(최신 데스크톱 CPU) 346ms, Fargate(2019년 서버 CPU) 991ms였다.

## 20. 프롬프트 캐싱
- 요청의 앞부분(도구 정의 → 시스템 프롬프트 → 메시지 순서)이 이전 요청과 바이트 단위로 같으면, 표시(`cache_control`)를 둔 곳까지를 캐시에서 읽는다. 캐시 읽기는 입력 단가의 1/10, 5분 캐시 쓰기는 1.25배다. 캐시는 5분 동안 쓰이지 않으면 사라진다(읽으면 연장).
- 이 에이전트는 호출 한 번 입력 약 2,600토큰 중 약 2,200토큰이 매번 같은 도구 정의와 시스템 프롬프트라, 시스템 블록 끝에 표시 하나를 두었다. 입력 비용이 약 75% 줄었다(test 78문항, 직접 측정). 모델에 들어가는 내용은 같아서 답은 바뀌지 않는다.
- 주의: langchain-anthropic의 `input_tokens`는 캐시 읽기·쓰기를 포함한 합계라 캐싱해도 토큰 수는 거의 같다. 효과는 비용으로 봐야 한다. 쓰기 토큰은 `cache_creation`이 아니라 TTL별 키(`ephemeral_5m_input_tokens`)에 들어 있었다.

## 21. Langfuse와 OpenTelemetry (직접 겪은 것)
- **트레이스와 관측(observation)**: 요청 하나가 트레이스 하나이고, 그 안에 LLM 호출(GENERATION), 도구 호출(TOOL), 그래프 노드(CHAIN, AGENT)가 부모-자식 구조로 들어간다. 각 관측에 시간, 입력·출력, 토큰, 비용이 붙는다.
- **점수(score)**: 트레이스에 붙이는 평가 값. 이 프로젝트는 규칙 채점 결과(`pass`, `format_ok`, `tool_exact`)를 붙여 "어느 문항이 왜 틀렸나"를 트레이스에서 바로 본다.
- **결정적 트레이스 ID**: 외부 ID(요청 ID, `run_id:문항 ID`)를 시드로 32자리 ID를 만들면, 로그나 결과 파일만 보고도 트레이스를 찾을 수 있다.
- **OpenTelemetry**: 트레이스를 만들고 보내는 표준. Langfuse 5.x SDK는 이 위에 만들어져서, 같은 프로세스의 **다른 라이브러리가 만든 span도 함께 보낸다.** Anthropic SDK가 자체 span을 만들어 LangChain 콜백의 기록과 같은 LLM 호출이 두 번 남았고 비용이 두 배로 합산됐다. 라이브러리의 자체 계측을 끄거나(`ANTHROPIC_OPEN_TELEMETRY=false`) 한쪽만 남겨야 한다.
- 관측 도구의 비용 계산은 그 도구의 단가표를 따른다. Langfuse의 캐시 읽기 단가($0.10)가 공시 단가($0.20)와 달랐다. 비용 판정은 자체 계산으로 하고 도구 값은 참고로 쓴다.

## 22. 멀티 에이전트를 언제 쓰나 (직접 측정한 것)
- 구조: 감독이 전문가를 도구처럼 부르는 방식("agents as tools"). 전문가는 자기 도구로 여러 단계를 처리하고 결과를 글로 보고한다.
- 비용 구조: 위임 결정, 전문가 실행, 보고 작성, 종합이 각각 LLM 호출이라 단일 에이전트보다 호출이 많다. 이 프로젝트에서는 3.2배 호출, 비용 2.1배, 지연 2.2배였고 정답률은 같았다(30/30).
- 기대한 "컨텍스트 분리" 이점은 **핸드오프 손실**로 상쇄됐다. 전문가가 90개 목록을 글로 넘기다 출력 상한(사고 토큰 포함)에 걸려 빈 보고가 9건 생겼고, 감독이 재위임했다.
- 그래서 멀티 에이전트는 "에이전트가 틀린다"는 근거와 그 원인이 구조로 풀린다는 근거가 있을 때 쓴다. 강한 단일 에이전트가 이미 맞히는 문제에 나누면 비용과 지연만 는다. 나눈다면 보고 형식(구조화), 출력 상한, 전달할 정보의 양을 먼저 설계한다.
