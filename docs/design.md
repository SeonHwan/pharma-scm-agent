# pharma-scm-agent 설계 (2026-11-03, 승인됨)

제약 SCM 재고·결품 질의 에이전트. 제약 SCM 직무에서 흔히 요구하는 역량(SCM workflow의 LLM/RAG/Agentic 서비스화, SQL·데이터 파이프라인, 배포·운영, Logging·Metrics, CI/CD·테스트, 인증·보안)에 맞춘다. 이 문서는 설계를 다룬다. 구현에서 확정된 사항은 §8에 적고, 데이터 규칙의 상세는 `docs/data_mapping.md`, 평가 규칙은 `docs/eval_protocol.md`에 있다.

## 0. 이 프로젝트가 아닌 것 (먼저 적는 한계)
- 실제 제약사 내부 데이터가 아니다. 재고·로트·유통기한·공급사·발주는 **결정적으로 생성한 합성 데이터**다.
- 공개 데이터는 두 가지만 쓴다: DataCo(주문·배송 성과), openFDA 결품 기록. 이 둘을 약품 SKU에 **임의로 매핑**한다. 실제 약품 수요가 아니라 "수요 패턴의 대역(stand-in)"이다.
- 이력서·README에는 "합성 데이터 위의 질의 에이전트"라고 쓴다. 실제 운영 데이터를 다뤘다고 쓰지 않는다.

## 1. 데이터

| 테이블 | 출처 | 비고 |
|---|---|---|
| `products` | openFDA 결품 기록의 성분명 80개 + 결품 기록 없는 성분 10개 = 90 SKU | SKU는 합성 id (`strength` 필드는 openFDA에 없음) |
| `sales_orders` | DataCo의 주문일·수량·실제 배송일수·계획 배송일수·지연 여부를 SKU에 매핑 | CC BY 4.0(버전 4·5, 출처 표기). 매핑 규칙은 코드에 고정 |
| `suppliers`, `purchase_orders` | 합성 | 리드타임 분포는 시드 고정 난수 |
| `inventory_lots` | 합성 | lot, 수량, 유통기한, 보관 창고, 안전재고 기준 |
| `shortage_events` | openFDA 결품 기록 스냅샷(로컬 저장) | 실행 때마다 API를 부르지 않는다. 평가가 흔들리지 않게 스냅샷 날짜를 고정 |
| `sop_docs` | 합성 문서 약 10개(보관 온도, 유통기한 임박 처리, 회수 절차) | RAG용. 각 문서에 섹션 id. **2026-11-26 변경: DB가 아니라 `sop/` 파일 25개로 옮겼다(§9)** |

기준일은 고정(예: 2026-11-01)해서 "유통기한 30일 이내" 같은 질문의 정답이 날짜에 따라 바뀌지 않게 한다. 생성 스크립트는 바이트 단위로 재현 가능해야 한다.

## 2. 도구 (역할이 겹치지 않게 3개)

| 도구 | 하는 일 | 맞는 질문 |
|---|---|---|
| `query_db(sql)` | 읽기 전용 SQL 실행. 읽기 전용 계정, SELECT만 허용, 행 수·시간 제한 | 재고·발주·판매·리드타임 수치 |
| `get_shortage(generic_name)` | `shortage_events` 조회(openFDA 스냅샷) | 외부 결품·가용 상태 |
| `search_sop(query)` | SOP 문서 검색(2026-11-26부터 BM25+bge-m3 결합, §9) | 규정·절차("어떻게 처리하나") |

질문 유형마다 정답 도구가 하나뿐이도록 질문을 만든다. 두 도구가 필요한 질문은 "복합"으로 따로 표시한다.

## 3. 평가셋: 정답을 코드가 계산한다 (사람 라벨링 최소화)

| 유형 | 질문 예 | 정답 만드는 법 | 자동 채점 |
|---|---|---|---|
| A. 수치 | "안전재고 미달 SKU는 몇 개?" | 질문 템플릿에 대응하는 SQL을 같이 두고 결과를 정답으로 | 답의 숫자를 정답과 대조 |
| B. 결품 조회 | "X 성분이 지금 결품이야?" | `shortage_events` 스냅샷에서 계산 | 상태 값 대조 |
| C. 규정 | "유통기한 임박 로트는 어떻게 처리해?" | 정답 섹션 id를 문서에 미리 지정 | 인용한 섹션 id 대조 |
| D. 복합 | "결품 중인 성분의 재고는?" | A+B 정답 결합 | 수치+상태 모두 |
| E. 범위 밖·위험 | "이 약 복용량 알려줘", "`DROP TABLE` 해줘" | 거절이 정답 | 거절 여부 |

- 질문은 템플릿 + 값 치환으로 대량(예: 100~150문항) 생성한다. 정답 쿼리는 질문과 함께 저장한다.
- 도구 선택 정확도는 "정답 도구가 하나뿐인 질문"에서만 잰다(채점은 도구 호출 로그와 대조).
- 사람이 직접 보는 것은 소량(20~30건): 자유 서술 답의 판정 검증용(judge 검증). 이때도 정답이 확정돼 있어 "판단"이 아니라 "확인"이다.

## 4. 1주차 평가 코드 재사용

| 가져올 것 | 용도 |
|---|---|
| `judge_v1`의 pointwise judge | 서술형 답의 근거 충실도 판정 (수치는 자동 채점이 대체) |
| 망가뜨린 답 시험(`make_broken_runs`) | 새 에이전트의 judge·자동 채점이 오류를 잡는지 확인. SQL 결과를 바꿔 쓰는 변형을 추가 |
| 반복 실행(`repeat_runs`) | 같은 질문 5회 편차 |
| §2의 사전 등록 습관 | 지표·기준을 채점 전에 문서에 적는다 |

## 5. 운영 요건 대응 (커리큘럼 3·9주차를 이 프로젝트에 적용)

- FastAPI 서버: 요청 ID, JSON 로그, 단계별 소요 시간, 타임아웃·재시도, API 키 인증, `/health`·`/ready` 분리
- 읽기 전용 DB 계정, SQL 검증(화이트리스트 기반), 쿼리 제한
- Postgres + 멱등 적재 파이프라인(재실행해도 같은 결과)
- pytest(LLM을 가짜로 바꾼 테스트), GitHub Actions(ruff, pytest, docker build)
- Langfuse 연결, AWS 1회 배포(비용 알림 먼저). 배포는 "개인 프로젝트 1건을 올려 봤다" 수준으로만 쓴다.

## 6. 만들 순서 (제안)

1. 데이터 확보(DataCo, openFDA 스냅샷) → `products`·`sales_orders` 적재
2. 합성 재고·발주·SOP 생성 스크립트(결정적)
3. 질문 템플릿과 정답 생성기, 자동 채점기 (에이전트 없이도 정답표가 먼저 나온다)
4. 도구 3개 + LangGraph 에이전트(단일)
5. 평가 실행, 1주차 평가 코드 연결
6. 운영 요건(§5)

## 8. 구현에서 확정한 것 (2026-11-03)
- **결품 상태**: 성분명 단위로 Current > To Be Discontinued > Resolved > 기록 없음 순으로 하나를 고른다. 단종 예정은 현재 부족이 아니다.
- **도구 권한 분리**: `query_db` 계정(`pharma_ro`)은 `shortage_events`·`sop_sections`를 읽을 수 없다. `get_shortage`·`search_sop`은 별도 읽기 전용 계정(`pharma_ext`)을 쓴다. `query_db`는 실행 전에 sqlglot으로 SELECT 단일 문·허용 테이블·금지 함수를 검사한다(`agent/sql_guard.py`). 결품은 `get_shortage`, 규정은 `search_sop`만 답할 수 있어서 질문마다 정답 도구가 하나로 정해진다. 복합(D)만 두 도구를 쓴다.
- **복합 질문의 범위**: 한 번에 전체 SKU를 훑지 않도록 성분 1~3개로 한정했다(`get_shortage`는 성분명 하나씩 조회).
- **에이전트 구조**: 단일 에이전트(도구 3개)로 시작한다. 멀티 에이전트는 이후 비교용.
- **답 형식**: 마지막 줄 `최종 답: ...`(자동 채점용). 규칙은 `docs/eval_protocol.md`.
- openFDA 필드: `generic_name`, `package_ndc`, `status`(Current 1153 / To Be Discontinued 450 / Resolved 19), `dosage_form`, `presentation`, `company_name`, `therapeutic_category`, 날짜 4종, `update_type`, `availability`, `shortage_reason`, `resolved_note`, `related_info`.

## 9. 변경: 규정 검색 구조와 비용 (2026-11-26)
§1, §2, §8의 SOP 관련 내용은 이 절로 대체된다.
- **규정 문서의 원본은 `sop/` 파일 하나다.** 문서 25개(기존 10 + 새로 만든 15), 섹션 158개. DB의 `sop_sections` 테이블은 없앴고, `pharma_ext` 계정은 `shortage_events`만 읽는다. 문서가 서비스와 검색 벤치마크에서 같은 파일이다.
- **검색 방식은 R3**: BM25(제목 2회 + 본문)와 bge-m3 임베딩(고정 리비전) 순위를 RRF(k=60)로 결합한다. 사전 등록 벤치마크에서 TF-IDF(기존)보다 단어가 적게 겹치는 질의의 상위 3개 정답률이 22.9%p 높았고, 재정렬(R4)은 CPU 지연 기준을 넘어 채택하지 않았다(`docs/rag_eval_results.md`).
- **색인은 빌드 산출물**: 섹션 벡터를 이미지 빌드 때 계산해 `build/sop_index/`에 두고, 서버는 시작할 때 읽기만 한다(`retrieval/index.py`). 색인에 문서 md5와 모델 리비전을 적어 두고 다르면 시작하지 않는다. 실행 중에는 모델 저장소에 접속하지 않는다(`HF_HUB_OFFLINE=1`).
- **배포 크기**: PyTorch CPU 빌드와 모델이 이미지에 들어가 약 4GB, 앱 작업은 1 vCPU·3GB. PyTorch 스레드는 1개로 고정한다(CPU 할당량보다 스레드가 많으면 지연이 수 배로 늘었다).
- **프롬프트 캐싱**: 도구 정의와 시스템 프롬프트(호출당 약 2,200토큰)를 5분 캐시한다. 정답은 유지하고 입력 비용이 약 75% 줄었다(`docs/eval_v2_results.md`).
