# 규정 검색(RAG) 평가 사전 등록 (2026-11-25)

이 문서는 **실험 결과를 보기 전에** 비교 방식, 지표, 판정 기준을 적는다. 결과를 본 뒤에는 이 문서의 규칙을 바꾸지 않는다. 바꿔야 하면 새 날짜의 절을 추가하고 이유를 적는다. 이 프로젝트의 데이터는 합성이다(`docs/data_mapping.md`).

## 1. 왜 먼저 문제를 어렵게 만드는가
- 현재 규정 코퍼스는 합성 SOP 문서 10개, 섹션 30개, 합계 약 7.6KB다. 평가 문항 중 규정 유형(C) 20개는 각각 정답 섹션이 하나이고, 질문이 섹션과 같은 단어를 쓴다.
- 현재 검색(`search_sop`, 글자 2-gram TF-IDF)은 이 문항에서 top-1 20/20으로 기록돼 있다(개발 초기 오프라인 검증 기록, 근거와 재현 방법은 §10). **이미 천장이라 방식을 바꿔도 차이를 잴 수 없다.**
- 그래서 (1) 섹션 수를 늘리고 비슷하지만 다른 규정을 의도적으로 섞은 코퍼스와, (2) 질문이 섹션과 단어를 덜 공유하는 질의를 만든 **검색 벤치마크**를 먼저 고정하고, 그 위에서 방식을 비교한다.
- 이 벤치마크도 합성이다. 현실의 규정 문서와 사용자 질문이 아니므로, 결과는 "이 합성 벤치마크에서의 차이"로만 해석한다.

## 2. 코퍼스 v2 (고정 후 재생성하지 않는다)
- 기존 섹션 30개(`SOP-nn-m`)는 id와 내용을 바꾸지 않는다.
- 문서 약 25개, 섹션 약 150~200개로 늘린다. 새 섹션 id는 같은 형식(`SOP-nn-m`)을 쓴다.
- **혼동 쌍을 의도적으로 넣는다**: 같은 주제인데 단계·대상·수치가 다른 섹션(예: 입고 시, 보관 중, 운송 중의 온도 일탈 대응. 회수, 격리, 반품, 폐기의 승인자와 기한). 각 섹션은 그 섹션에만 있는 사실(수치, 기한, 승인자 같은 조건)을 최소 하나 가진다.
- 생성은 Claude로 초안을 만들고, **저장한 파일을 그대로 쓴다**(다시 생성하지 않는다). 생성 뒤 코드로 형식(제목 규칙, 섹션 id 중복 없음)과 "섹션의 고유 사실(수치)이 다른 섹션에 같은 문맥으로 중복되지 않음"을 검사한다. 합성임을 각 문서에 명시한다.
- 고정 후 파일 목록의 md5를 등록한다(`eval/registered.json`과 같은 방식).

## 3. 질의 셋
- 질의마다 정답 섹션 id는 **하나**다(그 질의가 묻는 고유 사실이 있는 섹션).
- 두 부류를 만든다. 어느 부류인지는 **질의 생성 방법으로 정하지 않고 코드가 계산한 값으로 나눈다**.
  - 겹침 비율 = 질의의 글자 2-gram 중 정답 섹션 본문(제목 포함)에 들어 있는 것의 비율.
  - **낮은 겹침 부류 = 겹침 비율이 전체 질의의 중앙값 이하**, 나머지는 높은 겹침 부류. 임계값을 데이터를 본 뒤에 고르지 않으려고 중앙값 규칙으로 고정한다.
- 질의 생성: 섹션마다 "섹션의 고유 사실을 묻되, 섹션의 표현을 그대로 쓰지 않고 바꿔 말하거나 구어체·줄임말로 쓴다"는 지시로 1~2개 만든다. 기존 규정 문항 20개는 그대로 포함하며 이 문항들은 "v1 문항"으로 따로 표시한다.
- 규모 목표: 약 100~120개(기존 20개 포함). 모호한 질의(정답 섹션 외 다른 섹션도 답이 될 수 있는 것)는 코드 규칙(질의가 묻는 수치가 다른 섹션에도 같은 문맥으로 있으면 제외)과 사람 확인(샘플 20개, 사용자가 원할 때)으로 걸러낸다. **Claude가 만든 질의를 Claude가 걸러내는 순환이 있으므로**, 사람 확인은 이 한계를 줄이는 장치이고 완전한 해결이 아니다.

## 4. 비교할 방식 (고정)
| 이름 | 방식 |
|---|---|
| R0 | 현재 방식: 글자 2-gram TF-IDF 코사인(`agent/tools.py`) |
| R1 | BM25(같은 글자 2-gram 토큰) |
| R2 | 밀집 임베딩 검색. 모델 하나를 고정: `BAAI/bge-m3`(다국어). 이 PC에서 로드할 수 없으면 `intfloat/multilingual-e5-small`로 바꾸고 바꿨다는 사실과 이유를 결과 문서에 적는다 |
| R3 | R1과 R2의 순위를 RRF(Reciprocal Rank Fusion, k=60)로 합침 |
| R4 | R3의 상위 20개를 교차 인코더 리랭커(`BAAI/bge-reranker-v2-m3`)로 재정렬 |

- 검색 결과 개수는 현재 도구와 같은 3개(k=3)를 기본으로 한다. 지표는 k=1, 3에서 잰다.
- 임베딩과 리랭커는 로컬에서 돌린다(LLM API 호출 없음, 모델 파일 다운로드 필요).

## 5. 지표
- **recall@1, recall@3**(정답 섹션이 상위 k에 있는 질의 비율), **MRR**. 전체와 부류별(낮은 겹침/높은 겹침, v1 문항)로 보고한다.
- 각 값에 Wilson 95% 구간을 붙인다.
- 지연: 질의당 시간의 중앙값과 p95(밀리초), 인덱스 구축 시간은 따로 적는다. 같은 PC에서 모든 방식을 같은 조건으로 잰다.

## 6. 판정 규칙 (이 규칙으로만 "채택"을 말한다)
- **채택 후보**는 R3 또는 R4다. 기준은 아래 둘을 모두 만족하는 것이다.
  1. **낮은 겹침 부류의 recall@3**이 R0보다 **10%p 이상** 높고, 두 값의 95% 구간이 겹치지 않는다.
  2. 지연 상한: R3는 질의당 p95 1초 미만, R4는 p95 2초 미만(에이전트가 한 번의 도구 호출로 쓰는 시간이므로).
- 기준을 만족하는 방식이 둘이면 더 단순한 쪽(R3)을 고른다. 하나도 만족하지 못하면 **현재 방식(R0)을 유지하고 "차이 없음"으로 적는다.**
- 기준을 결과를 보고 바꾸지 않는다. 구간이 겹치면 점추정이 높아도 "차이가 있다"고 쓰지 않는다.

## 7. 알려진 한계 (미리 적는다)
- 코퍼스와 질의가 모두 합성이고 질의를 만든 모델과 코퍼스를 만든 모델이 같다. 실제 사용자 표현과 다를 수 있다.
- 150~200개 섹션은 실제 규정 문서 규모보다 작다. 이 규모에서 리랭커의 이득이 작게 나올 수 있다.
- 질의 100개 안팎이라 구간이 넓다(예: 낮은 겹침 부류는 약 50개). 10%p 차이를 구간으로 구분하지 못하면 "차이 없음"이다.
- 이 단계는 **검색만** 평가한다. 검색이 좋아졌을 때 에이전트의 최종 답이 좋아지는지는 평가셋 v2 단계에서 따로 본다.

## 8. 진행 순서와 비용
1. 코퍼스 v2와 질의 생성(Claude 호출, 추정 비용을 계산해 승인받은 뒤 실행) → 코드 검사 → 사람 확인(선택) → 파일 고정과 md5 등록
2. 검색 방식 R0~R4 구현(`src/pharma_scm/retrieval/`), 기존 테스트가 깨지지 않는지 확인
3. 벤치마크 실행(LLM 호출 없음) → 결과를 `docs/rag_eval_results.md`에 이 문서의 규칙 그대로 기록
4. 채택 결과가 나오면 `search_sop`에 연결하고 영향(에이전트 답)을 평가셋 v2 단계에서 확인한다

## 9. 실행 전 보정 (2026-11-25, 아직 어떤 결과도 보지 않았다)
위 1~8절의 규칙은 바꾸지 않는다. 구현을 구체화하면서 정해야 했던 것을 결과를 보기 전에 추가한다.

### 9-1. 사용 모델 (생성과 검증을 서로 다른 회사 모델로)
| 역할 | 모델 | 이유 |
|---|---|---|
| 코퍼스 생성 | Claude Sonnet 5.5 | 코퍼스의 난이도는 주제 목록, 혼동 관계, 코드 검사로 통제한다 |
| 질의 생성 | Claude Opus 5.5(코퍼스 전체를 캐시된 맥락으로 전달) | 질의가 묻는 사실이 정답 섹션에만 있는지 코퍼스 전체를 보고 판단해야 한다 |
| 질의 검증 | OpenAI `gpt-6.1-terra`(사용자 보고 단가: 입력 $1, 캐시 입력 $0.05, 출력 $5 per 100만 토큰. 비교 대상 `gpt-5.6-terra`는 $2, $0.20, $12라 6.1이 더 싸서 6.1로 확정) | 질의를 만든 모델과 **다른 회사 모델**이 독립적으로 점검해 같은 계열 모델끼리 통과시키는 순환을 줄인다 |
- 에이전트는 Claude Sonnet 5.5이므로, 질의 검증을 다른 회사 모델이 하는 것이 이 벤치마크의 독립성을 높이는 장치다. 코퍼스와 질의를 같은 회사 모델이 만든다는 한계(7절)는 그대로 남는다.

### 9-2. 코퍼스 위치
- 기존 `sop/`(문서 10개, 섹션 30개)는 **바꾸지 않는다.** 에이전트, DB 적재, 평가 문항(`eval/questions.jsonl`), 스냅샷(`deploy/pharma.sql.gz`)이 이 30개 섹션을 전제로 한다.
- 새 문서 15개는 `eval/rag/corpus_v2/`에 둔다. 벤치마크는 `sop/`와 `eval/rag/corpus_v2/`를 합친 것을 코퍼스로 읽는다. 새 코퍼스를 에이전트에 연결할지는 검색 방식이 채택된 뒤 별도로 정한다(4번 항목).

### 9-3. 질의 수
- 새 문서 15개의 섹션마다 질의를 **1개**씩 만든다(약 120~130개). 기존 규정 문항 20개를 합쳐 **약 140~150개**다. 3절의 "약 100~120개"를 이것으로 바꾼다. 기존 30개 섹션에 대한 새 질의는 만들지 않는다(기존 20개 문항이 이미 있다).

### 9-4. 검증 패스와 제외 규칙 (검색 방식을 측정하기 전에 끝낸다)
- 질의를 만든 뒤, 검증 모델에게 코퍼스 전체와 질의 묶음(한 번에 약 25개)을 주고 "각 질의에 답할 수 있는 섹션을 **모두** 고르라"고 한다.
- 검증 모델이 고른 집합이 정답 섹션 하나와 **다르면** 그 질의를 표시한다. 표시된 질의는 사용자 확인 샘플에 우선 포함하고, 사용자가 유지하기로 한 것만 남기고 나머지는 제외한다. 제외한 수와 이유를 결과 문서에 적는다.
- 제외는 **검색 방식(R0~R4)을 한 번도 실행하기 전에** 끝내고, 그 뒤에는 질의 셋을 바꾸지 않는다. 방식의 성적을 보고 질의를 고르는 것을 막기 위한 순서다.
- 사용자 확인 샘플 20개: 표시된 질의를 우선 포함하고, 모자라면 나머지에서 시드 고정 난수로 뽑는다.

### 9-5. 비용
- 호출 수와 토큰은 `--dry-run`으로 먼저 센다. 실행 전에 사용자의 승인을 받는다. 비용 상한은 승인할 때 적는다.
- 실제 사용한 모델, 호출 수, 토큰, 비용은 결과 문서에 적는다.

### 9-6. 검증기의 검출력 확인: 통제 질의 (검증 128개 결과를 본 직후, 통제 질의 실행 전에 적는다)
- 배경: 검증 모델은 128개 중 125개에서 정답 하나만 골랐고 3개에서 여러 개를 골랐다. 이 "일치"가 질의가 좋아서인지 검증기가 하나만 고르는 경향 때문인지 구분하려고, **답이 둘 이상이 되도록 일부러 만든 질의**와 **코퍼스에 답이 없는 질의**를 같은 방식으로 검증기에 넣는다.
- 통제 질의 8개를 코퍼스를 읽고 작성한다(`eval/rag/verifier_controls.jsonl`).
  - 모호 통제 6개: 같은 질문에 답을 줄 수 있는 섹션이 코퍼스에서 둘 이상이다(예: 온도 기록 간격, 기록 보관 기간, 온도 일탈 통보). 기대 섹션 목록을 함께 적는다.
  - 답 없음 통제 2개: 코퍼스에 근거가 없는 질문(예: 약국 개설 허가, 직원 휴가)이다. 기대는 빈 목록이다.
- 판정(사전 등록): 모호 통제는 검증기가 **2개 이상**을 고르고 그중 **기대 섹션이 하나 이상** 있으면 통과, 답 없음 통제는 **빈 목록**이면 통과한다.
- 해석 규칙:
  - 모호 통제 6개 중 **4개 이상 통과**하고 답 없음 통제 2개가 모두 통과하면 "검증기는 둘 이상의 답과 답 없음을 가려낼 수 있다"고 보고, 128개의 검증 결과를 사용한다.
  - 그렇지 않으면 128개의 "일치"를 **확인된 것으로 해석하지 않는다.** 검증 모델의 생각 깊이를 높이는 등 방법을 바꿔 새 날짜의 절로 적고 다시 검증한다.
- 통제 질의는 벤치마크 질의에 **포함하지 않는다**(검증기 점검용이다).
- 표시된 질의(검증기가 정답과 다른 집합을 고른 것, 또는 정답과 같지만 메모를 단 것)는 **정답과 같은 섹션을 골랐더라도 메모가 있으면 사용자 확인 샘플에 먼저 넣는다.**

### 9-7. 알려진 코퍼스 한계 (점검 중 발견, 2026-11-25)
- 혼동 쌍을 "다른 값"으로 만들게 한 결과 **문서 간 규정이 모순되는 곳이 있다.** 예: 온도 기록 보관 기간이 SOP-02-1에서 3년, SOP-11-9에서 5년, SOP-15-4에서 계약 종료 후 5년, SOP-22-2에서 7년이다. 검색 벤치마크에서는 "같은 주제, 다른 단계·대상"이 구분되는 질의로 의도한 난이도이지만, 에이전트가 이 코퍼스로 답하는 단계에서는 별도의 한계로 다룬다.

### 9-8. 사용자 검토 결과와 질의 고정 (2026-11-25, 검색 방식 R0~R4를 실행하기 전)
- 검토 샘플 20개(표시된 6개 + 무작위 14개, `eval/rag/review_sample_v2.json`)를 사용자가 O/X로 판정했다(`eval/rag/review_v2.jsonl`).
- 결과: **표시된 6개 중 X 2개**(SOP-23-1, SOP-11-9), **무작위 14개 중 X 0개**. 표시되지 않은 질의에서는 문제가 나오지 않았다.
- 제외: X 2개. 최종 질의는 새 섹션 질의 **126개**(`eval/rag/queries_v2_final.jsonl`)와 기존 규정 문항 20개(`eval/questions.jsonl`의 C유형)를 합친 **146개**다. 3절과 9-3의 "약 140~150개" 범위 안이다.
- 제외 이유(요약): SOP-23-1은 질의의 "보류"가 무엇인지 불분명하고 코퍼스 안에서 SOP-23-1과 SOP-23-2가 충돌한다(사용자 판단). SOP-11-9는 SOP-22-2와 온도 기록 보관 기준이 중첩된다(사용자는 사유를 적지 않았고, 검증 모델의 메모를 참고로만 적었다).
- 표시되었지만 O로 판정된 질의(SOP-14-3, 18-2, 19-7, 21-3)는 유지한다.
- 표본이 20개(전체 128개의 약 16%)라서, 샘플 밖 질의에 같은 문제가 없다고 단정하지 않는다. 무작위 14개에서 문제가 0개였다는 것은 문제 비율이 높지 않다는 약한 근거일 뿐이다(14개 전부 정상일 때 문제 비율의 95% 신뢰 상한은 약 20%).
- 이 시점 이후 질의 셋은 바꾸지 않는다. md5를 `eval/rag/registered.json`에 등록한다.
- 코퍼스 안의 충돌(SOP-23-1과 SOP-23-2의 예외 불출 허용 범위)도 9-7의 한계에 더한다.

### 9-9. 코퍼스를 sop/ 하나로 합침 (2026-11-26, 벤치마크 실행 뒤 구조 변경)
- 벤치마크 결과(`docs/rag_eval_results.md`)를 본 뒤, 검색을 에이전트에 연결하기 위해 구조를 바꿨다. 새 문서 15개를 `eval/rag/corpus_v2/`에서 `sop/`로 옮겨 **규정 문서의 원본을 `sop/` 하나로** 만들었다. 서비스하는 문서와 벤치마크가 같은 파일을 쓴다.
- **파일 내용은 바뀌지 않았다.** 25개 파일 모두 파일 이름과 md5가 이전 등록값과 같고, 등록 파일(`eval/rag/registered.json`)의 경로 키만 바뀌었다. 따라서 이미 실행한 벤치마크 결과는 이 코퍼스에 그대로 해당한다.
- 9-2의 "기존 `sop/`는 바꾸지 않는다"는 이 시점부터 적용하지 않는다. 에이전트, DB, 평가 문항이 30개 섹션을 전제로 하던 부분은 이어지는 커밋에서 새 구조에 맞춘다(DB에서 SOP 테이블 제거, 검색 모듈 교체, 평가 기준선 재측정).

## 10. §1 기록의 근거 보완 (2026-11-27, 규칙 변경 아님)
- §1의 "top-1 20/20"은 에이전트 코드를 처음 만들 때(2026-11-06 무렵) LLM 없이 돌린 오프라인 검증의 기록이고, 그때의 측정 파일은 저장소에 남기지 않았다. 당시 검색 코드(`agent/tools.py`의 `run_search_sop`)는 이후 R3로 교체되어 지금 저장소에 없다.
- 그래서 같은 계산을 지금 코드로 다시 쟀다. `src/pharma_scm/retrieval/methods.py`의 R0(`TfidfCosine`, 위 `run_search_sop`와 같은 글자 2-gram TF-IDF 코사인)를 기존 문서 10개·섹션 30개(`SOP-01`~`SOP-10`, §2대로 id와 내용 불변)에 대해 만들고, `eval/questions.jsonl`의 규정 유형(C) 20문항 질문으로 1위 섹션을 정답 섹션과 대조했다. 결과 **top-1 20/20**으로 §1의 기록과 같다. LLM 호출은 없다.
- 재현(저장소 루트, 색인·DB 불필요):

```python
import json
from pharma_scm.retrieval.corpus import load_corpus
from pharma_scm.retrieval.methods import TfidfCosine

secs = [s for s in load_corpus() if int(s["doc_id"].split("-")[1]) <= 10]  # 섹션 30개
r = TfidfCosine(secs)
c = [q for q in map(json.loads, open("eval/questions.jsonl", encoding="utf-8")) if q["type"] == "C"]
print(sum(r.rank(q["question"])[0] == q["gold"]["value"] for q in c), "/", len(c))
```
