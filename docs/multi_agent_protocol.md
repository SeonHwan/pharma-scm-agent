# 멀티 에이전트 대 단일 에이전트 비교: 사전 등록 (2026-11-26, 본 평가 실행 전)

## 1. 질문
같은 모델, 같은 도구, 같은 프롬프트 문구에서 **구조만** 바꿨을 때(단일 에이전트 S → 감독 + 전문가 3 멀티 에이전트 M), 정답률이나 비용이 나아지는가.

## 2. 비교 대상
| 이름 | 구조 | 코드 |
|---|---|---|
| S | 단일 에이전트. 도구 3개(`query_db`, `get_shortage`, `search_sop`), 프롬프트 v1(`b92313567d93`), 프롬프트 캐싱 | `agent/graph.py build_graph` |
| M | 감독 에이전트가 전문가 에이전트 3개를 도구처럼 부른다(`ask_db_analyst`, `ask_shortage_specialist`, `ask_sop_specialist`). 전문가는 각자 도구 하나로 여러 단계를 처리하고 글로 보고한다. 감독은 데이터 도구를 직접 쓰지 않는다 | `agent/multi.py` |

- 공통: `claude-sonnet-5-5`, max_tokens 2048, 도구 호출 상한 8(감독과 전문가 각각), 프롬프트 캐싱 표시, 같은 도구 구현.
- 프롬프트 문구: S의 시스템 프롬프트를 절로 나눠(`prompt.py`의 INTRO, TOOL_GUIDE, DATA_DICT, REFUSAL, ANSWER_FORMAT, 합치면 S와 바이트 단위로 같음) M이 나눠 쓴다. 감독 = INTRO + 역할 설명 + REFUSAL + ANSWER_FORMAT, DB 분석가 = 역할 + DATA_DICT, 결품 담당과 규정 담당 = 역할 설명. **M에만 있는 문구는 역할 설명(`*_ROLE`)뿐이다.**
- 집계: 전문가 안의 LLM 호출과 도구 호출까지 모두 세도록 토큰과 도구를 콜백(`observability.UsageCallback`)으로 모은다. S와 M에 같은 방식이다.
- M 구조는 이 문서 커밋 시점에 고정한다. 결과를 보고 M을 고치지 않는다(고치면 M2로 새로 등록).

## 3. 평가셋 v3 (`eval/questions_v3.jsonl`, 30문항, md5 `ee29b0a0bd1bde7e1c2b96c560812bae`)
만드는 코드: `src/pharma_scm/evalset/build_evalset_v3.py --main`. 정답은 DB와 결품 스냅샷에서 계산(결품 상태 규칙은 v1과 같음). 규칙 채점(`grader.py`), LLM judge 없음.

| 유형 | 수 | 내용 | 채점 |
|---|---|---|---|
| X | 12 | DB 조건(냉장, 격리, 유통기한, 공급사·국가, 재고 부족)과 외부 결품 상태를 합친 SKU 목록(11) 또는 개수(1). 성분마다 `get_shortage`를 불러야 한다 | SKU 집합 일치, 정수 일치 |
| Y | 8 | DB 결과(SKU 목록 4, 수치 4)와 근거 규정 섹션을 함께 | 둘 다 맞아야 정답(`set_section`, `number_section`, 섹션은 정답 포함이고 2개 이하) |
| Z | 2 | 규정 문서끼리 값이 다른 주제(온도 기록 3년/7년, 실사 기록 3년/5년) | 모순 섹션을 모두 적고 허용 목록 밖 섹션이 없어야 정답(`sections_conflict`) |
| L | 8 | 전 품목(90개)의 결품 상태를 봐야 하는 문항. 도구 결과가 약 4만 토큰 쌓인다(컨텍스트 부하) | 집합, 수치, SKU+수치 |

- 문항을 만들기 전에 파일럿 2회를 S로만 돌렸다(`eval/questions_v3_pilot*.jsonl`, 판정에 쓰지 않음). 1회(여러 도구·모순 10문항) 10/10, 2회(전 품목 5문항) 5/5. 본 평가는 파일럿과 같은 조건 조합을 쓰지 않았다. M은 파일럿 3문항으로 동작만 확인했다(3/3).
- **파일럿 결과로 보아 S가 본 평가도 만점에 가까울 가능성이 높다.** 그래서 이 비교의 주된 관심은 정답률보다 비용과 지연이다(아래 판정 규칙의 효율 조건).

## 4. 실행
- S와 M을 각각 30문항 전체에 1회 실행한다(작업자 3개, Langfuse 트레이스 켬). run_id `v3_S_<커밋>`, `v3_M_<커밋>`.
- dev/test 분할은 하지 않는다. M을 결과로 조정하지 않으므로 조정용 절반이 필요 없다.
- 실행 오류 문항은 같은 run_id로 그 문항만 다시 돌린다. 다시 돌려도 오류면 오답.

## 5. 판정 규칙 (30문항 짝지은 비교)
- **M 품질 채택**: M 정답 수 > S 정답 수, McNemar 정확 검정 p < 0.05.
- **M 효율 채택**(품질 채택이 아닐 때): M 정답 수 ≥ S 정답 수 − 1, 그리고 30문항 전체 비용(`report_v2.input_cost` + 출력 x $10/100만)이 S보다 20% 이상 적다.
- 둘 다 아니면 **S 유지**. 이때도 유형별 정답, 비용, 지연(문항별 `latency_s` 중앙값), LLM 호출 수 차이를 표로 남긴다.
- 참고(판정에 쓰지 않음): L 유형만의 비용·지연 비교, 실패 문항의 원인 분류(Langfuse 트레이스로 도구 누락, 계산 오류, 전달 중 정보 손실 등).

## 6. 비용 추정 (실행 전 승인)
파일럿 실측(S: X 평균 $0.063, Y·Z $0.02, L $0.431. M: 파일럿 3문항에서 S의 2.4배) 기준: S 약 $4.4, M 약 $10.6(2.4배가 L에도 그대로라고 가정, L에서 M이 오히려 쌀 수도 있다). **합계 약 $15.**

## 7. 알려진 한계 (결과를 보기 전에 적음)
- 문항은 30개이고 파일럿상 S가 상한에 가까워, 정답률 차이는 검정력이 거의 없다.
- 문항, 정답 규칙, M의 역할 설명을 모두 같은 계열 모델(Claude)이 썼다. M의 역할 설명을 더 다듬으면 결과가 달라질 수 있다(한 가지 설계만 잰다).
- 각 구조를 1회씩만 실행한다.
- 규칙 채점이 가능한 문항만 다룬다. 모호한 질문, 여러 턴 대화처럼 judge가 필요한 문항은 없다.
- Y와 Z의 정답 섹션은 v1 규정 문항과 코퍼스 확인으로 정했다. 새 문서 15개에 같은 주제를 다루는 다른 섹션이 있으면 맞는 답이 오답 처리될 수 있다(섹션 2개까지 허용으로 일부 완화).
