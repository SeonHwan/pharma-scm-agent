### 이 결과가 말하는 것
- **v2도 상한에 닿았다.** 정답 조건이 질문에 명시된 문항(규정 섹션 찾기, 정의가 적힌 DB 계산)에서는 현재 에이전트가 실패하지 않는다. 결과를 보기 전에 "어렵다"고 본 H(여러 테이블 조인, 날짜 구간, 단위 구분)도 30/30이었다.
- 따라서 사전 등록 §4의 **품질 개선 판정은 이 평가셋으로는 성립할 수 없다**(기준선이 78/78이라 개선안이 더 맞힐 문항이 없다). 남은 판정은 효율 개선(정답 유지, 입력 토큰 20% 이상 감소)뿐이다.
- dev 실패가 0건이므로 사전 등록 §3-2의 "dev 실패를 보고 개선안을 정한다"는 절차도 적용할 실패가 없다.
- 한계(사전 등록 §7)는 그대로다. 특히 G는 검색 방식을 고를 때 쓴 질의라 낙관적일 수 있다.

### 해석과 한계
- G075는 답 내용과 근거(SOP-19-8)가 기준선과 같았고 마지막 줄을 섹션 id 대신 `최종 답: 3`으로 써서 오답 처리됐다. 캐싱은 모델에 들어가는 내용을 바꾸지 않으므로 실행마다 달라지는 변동으로 본다(반복 측정은 하지 않음). v1 E009도 같은 성격이다.
- 측정한 모든 실행에서 캐시 쓰기가 0이었다. 직전 확인 호출로 캐시가 이미 만들어진 상태에서 5분 안에 이어서 실행했기 때문이다. 캐시가 비어 있으면 5분마다 한 번 쓰기(약 2,207토큰 x $2.5 = 약 $0.006)가 더해진다. 운영처럼 요청 간격이 5분을 넘으면 매 요청이 쓰기를 내므로 절감이 작아진다(1시간 TTL은 쓰기 단가가 2배라 따로 계산해야 한다, 측정하지 않음). 쓰기가 일어난 실행이 없어서, 고친 쓰기 집계(`ephemeral_5m_input_tokens` 포함)가 실제 응답에서 맞게 잡히는지는 확인하지 못했다.
- 지연은 줄지 않았다: v1 지연 중앙값 3.38s → 3.44s.
- 이번 개선은 비용만 바꾼다. 정답 조건이 명시된 문항에서 품질이 상한이라 컨텍스트 변경의 품질 효과는 이 평가셋으로 잴 수 없다. 모호한 질문, 문서 모순, 여러 턴 대화처럼 실제로 틀릴 수 있는 문항(평가셋 v3, LLM judge 또는 사람 검토 필요)은 멀티 에이전트 비교 단계에서 함께 설계한다.
- 이 단계 LLM 비용(추정): 기준선 약 $2.17, dev·test·v1 회귀와 확인 호출 약 $1.5.
