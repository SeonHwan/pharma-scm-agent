# 평가셋 v2와 컨텍스트 개선: 사전 등록 (2026-11-26, 결과를 보기 전에 확정)

v1(114문항)은 기준선 111/114, 새 검색 연결 뒤 113/114로 상한에 닿아 있어 어떤 변경도 차이를 보여 주지 못한다(`docs/rag_eval_results.md` §10). 이 단계는 (1) 상한에 닿지 않는 평가셋 v2를 만들고, (2) 에이전트의 컨텍스트(시스템 프롬프트, 도구 결과 형태)를 바꿨을 때 정답률이나 비용이 나아지는지 미리 정한 규칙으로 판정한다. v1과 그 결과는 바꾸지 않는다.

## 1. 평가셋 v2 (`eval/questions_v2.jsonl`, 156문항)
만드는 코드: `src/pharma_scm/evalset/build_evalset_v2.py`. 채점은 v1과 같은 규칙 채점기(`grader.py`)이고 LLM judge는 쓰지 않는다.

| 유형 | 수 | 출처 | 정답과 채점 |
|---|---|---|---|
| G. 새 규정 문항 | 126 | 검색 벤치마크에서 검증과 사용자 검토를 마친 질의(`eval/rag/queries_v2_final.jsonl`, md5 `488e6b55…`)를 순서대로 그대로 씀 | 질의를 만든 섹션 id. 마지막 줄의 섹션 id 집합에 정답이 있고 2개 이하면 정답(v1 C와 같은 규칙) |
| H. 어려운 DB 문항 | 30 | Claude(이 작업의 코딩 보조)가 직접 쓴 질문. 여러 테이블 조인, 날짜 구간, 단위(주문 수와 주문 항목 수), 소진 일수 같은 계산 정의를 **질문에 명시** | DB에서 SQL로 계산(`gold_sql`). 수치는 정수 일치 또는 소수 ±0.05, 목록은 SKU 집합 일치(v1 A와 같은 규칙) |

- 모순 규정(알려진 곳 3~4개, `docs/rag_eval_protocol.md` 9-7)은 통계를 낼 수 없어 문항으로 넣지 않는다. 사례로만 관찰한다.
- 등록: `eval/questions_v2.jsonl` md5 **`1483ecb542fd99a3c716891aea7ac6b4`**. 이후 문항과 정답은 바꾸지 않는다(바꾸면 v3).

## 2. dev/test 나누기
- 유형별로 문항 id를 시드 `20261126`으로 섞어 절반은 dev, 절반은 test로 나눈다(G 63/63, H 15/15, 합계 78/78). 각 문항의 `split` 필드에 기록한다.
- **개선안은 dev 결과만 보고 정한다.** test의 개별 결과는 최종 비교 전까지 열어 보지 않는다. 기준선 실행은 v2 전체에 돌리지만 test 쪽은 정답 수와 토큰 합계만 기록하고 실패 문항 내용은 보지 않는다.

## 3. 절차
1. **기준선**: 현재 에이전트(프롬프트 v1 `b92313567d93`, 검색 R3, `claude-sonnet-5-5`)로 v2 156문항 전체를 1회 실행한다. run_id `v2_v1_<커밋 8자>`.
2. **개선안 만들기(dev만)**: dev 실패를 분류하고 그에 맞는 컨텍스트 변경을 만든다. 후보는 미리 정하지 않는다. 예상 범위: 검색 결과에 문서·섹션의 적용 범위를 붙이기, 지표 정의(용어집) 추가, 검색 결과 수 조정, 도구 결과 줄이기. 바꾸는 범위는 시스템 프롬프트와 도구 결과의 형태로 한정한다(모델, 검색 방식 R3, 도구 수, 도구 호출 상한 8은 바꾸지 않는다).
3. 개선안을 dev 78문항에 돌린다. **dev 반복은 최대 3회**(후보 3개)다. 프롬프트를 바꾸면 `PROMPT_VERSION`을 올린다. 3회 안에서 dev 결과가 가장 좋은 후보 하나를 고른다(정답 수 우선, 같으면 입력 토큰이 적은 쪽).
4. **최종 비교(test, 1회)**: 고른 후보로 test 78문항을 1회 실행하고, 기준선의 test 결과와 짝지어 비교한다(`report_v2 <기준> <개선> --split test`).
5. **v1 회귀 확인**: 4에서 채택되면 v1 114문항 전체를 1회 실행해, 어느 유형도 `docs/rag_eval_results.md` §10 결과보다 2문항 이상 떨어지지 않는지 본다. 떨어지면 채택을 보류하고 원인을 기록한다.

## 4. 판정 규칙 (test 78문항, 짝지은 비교)
- **품질 개선으로 채택**: 개선안 정답 수 > 기준선 정답 수이고, McNemar 정확 검정(엇갈린 문항에 대한 양측 이항 검정) p < 0.05.
- **효율 개선으로 채택**(품질 개선이 아닐 때): 개선안 정답 수 ≥ 기준선 정답 수 − 1(78문항에서 2%p 이내 하락은 1문항까지)이고, 입력 토큰 합계가 20% 이상 적다.
- **둘 다 아니면 "차이 없음"**: 기준선을 유지하고 결과를 그대로 적는다.
- 실행 오류 문항이 있으면 그 문항만 다시 돌린다(같은 run_id, 이어서 실행). 다시 돌려도 오류면 오답으로 센다.

## 5. 지표와 도구
- `src/pharma_scm/evalset/report_v2.py`: 유형별 정답률(Wilson 95% 구간), 형식 위반, 실행 오류, LLM 호출 수, 입력·출력 토큰, 짝지은 비교(McNemar 정확 p, 입력 토큰 변화).
- `run_eval.py --set v2 [--split dev|test]`로 실행한다.

## 6. 비용 (실행 전에 dry-run으로 다시 계산해 승인받는다)
v1 실측(문항당 약 $0.013, Sonnet 5.5 입력 $2·출력 $10 /100만 토큰) 기준 추정: 기준선 156문항 약 $2, dev 반복 3회 약 $3, test 1회 약 $1, v1 회귀 확인 약 $1.5. 합계 약 $6~10.

## 7. 알려진 한계 (결과를 보기 전에 적음)
- G는 검색 방식(R3)을 고를 때 쓴 질의다. R3가 이 질의에서 좋게 나온 것이 선택 이유이므로 G의 에이전트 정답률은 낙관적일 수 있다. 다만 기준선과 개선안이 같은 R3를 쓰므로 둘의 비교에는 영향이 같다.
- G 질의와 규정 문서는 같은 계열 모델이 만든 합성 데이터이고, H는 에이전트와 같은 계열 모델(Claude)이 썼다.
- 각 조건을 1회씩만 실행한다. v1 반복 측정(30문항 x 5회 전부 통과)으로 변동이 작다는 근거는 있지만 v2에서 재지 않았다. McNemar 검정은 문항 표본의 변동만 다루고 실행마다 달라지는 변동은 다루지 않는다.
- test 78문항에서 p < 0.05가 되려면 엇갈린 문항이 한쪽으로 크게 쏠려야 한다(예: 0대6, 1대8). 작은 개선은 "차이 없음"으로 나올 수 있다.
- 개선안을 dev에서 고르므로 dev 결과는 낙관적이다. 판정에는 test만 쓴다.

## 8. 변경 기록 (개선안 실행 전에 적음)
### 8-1. 기준선이 상한이라 효율 판정만 남음, 개선안 선정 방식과 효율 기준 변경 (2026-11-26)
- 기준선이 156/156이었다(`docs/eval_v2_results.md` §1). dev 실패가 0건이라 §3-2("dev 실패를 보고 개선안을 정한다")를 적용할 수 없다. 대신 **dev 기준선의 토큰 구성**을 보고 개선안을 정했다: 호출 한 번의 입력 약 2,600토큰 가운데 대부분이 매 호출 반복되는 시스템 프롬프트와 도구 정의다.
- 개선안: **프롬프트 캐싱**. 시스템 프롬프트 블록 끝에 캐시 표시(`cache_control`, 5분)를 붙여 도구 정의와 시스템 프롬프트를 캐시한다. 프롬프트 문구, 도구, 모델은 그대로라 `PROMPT_VERSION`은 올리지 않고, 실행 메타와 결과에 `prompt_cache`를 기록한다.
- **§4의 효율 기준을 "입력 토큰 20% 감소"에서 "입력 비용 20% 감소"로 바꾼다.** 이유: 이 코드가 쓰는 langchain-anthropic의 `input_tokens`는 캐시에서 읽은 토큰과 캐시에 쓴 토큰을 포함한 합계라, 캐싱은 토큰 수를 줄이지 않고 단가를 줄인다(캐시 읽기는 입력 단가의 1/10, 5분 캐시 쓰기는 1.25배). 입력 비용 = 캐시 안 된 입력 x $2 + 캐시 쓰기 x $2.5 + 캐시 읽기 x $0.2 (100만 토큰당, Sonnet 5.5 공시 단가, 알고 있는 기준). 기준선은 캐시를 쓰지 않았으므로 입력 토큰 x $2다.
- 정답 조건(개선안 정답 수 ≥ 기준선 − 1)과 dev 최대 3회, test 1회, v1 회귀 확인은 그대로다. 품질 개선 판정은 기준선이 78/78이라 성립하지 않는다(§4 그대로 두되 해당 없음으로 기록).
- 실행 동시성(작업자 4개)은 기준선과 같게 둔다. 동시에 시작한 호출들은 서로의 캐시를 읽지 못하고 각자 쓸 수 있어 절감이 약간 작게 나올 수 있다.
